## Root Cause
In order_service.place_order the except ValueError: block re-raises the exception without calling release(product_id, qty) and remove_audit_entry(order_id). Concretely, after reserve(product_id, qty) sets inventory._reserved and add_audit_entry(...) appends into payment._audit_log, a payment.process(...) failure triggers the except clause that simply 'raise's again, leaving _reserved incremented and the audit entry present.

## Failure Mechanism
Example: inventory._stock['P1']=10. place_order('P1', 2, price) calls reserve('P1',2) -> inventory._reserved['P1'] becomes 2, then add_audit_entry({'order_id':'ORD-P1-2',...}) appends to payment._audit_log. If payment._gateway_fail is True then process(...) raises ValueError and the except branch re-raises without calling remove_audit_entry('ORD-P1-2') or release('P1',2). As a result, inventory.available('P1') returns 8 (stock 10 minus reserved 2) permanently (reserved was never released) and payment.get_audit_log() still contains the audit entry for an order that never completed.

## Broken Invariant
If place_order(...) raises (payment failure), then inventory.get_reserved(product_id) must NOT include the reserved qty for that failed order and payment.get_audit_log() must NOT contain an entry with order_id == f'ORD-{product_id}-{qty}'. Currently both are violated: reserved remains increased and the audit log still contains the order entry after a payment failure.

## Fix Strategy
Fixed place_order to perform compensating actions on any exception from payment.process: it now calls remove_audit_entry(order_id) and release(product_id, qty) before re-raising. This ensures the two mutated resources (inventory._reserved and payment._audit_log) are rolled back if process fails. Additionally fixed reset() to call inventory.reset() and payment.reset() so tests can reliably restore global state. The change is implemented in order_service.place_order: the except Exception handler performs rollback (remove_audit_entry, release) then re-raises the original exception.
