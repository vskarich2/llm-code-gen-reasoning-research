# Developer's Reasoning

## Root Cause
make_transfer_b_to_a_steps acquires locks in the opposite order from make_transfer_a_to_b_steps. Specifically, make_transfer_a_to_b_steps first calls acquire("A") then acquire("B") (via step_lock_a and step_lock_b_and_transfer), while make_transfer_b_to_a_steps first calls acquire("B") then acquire("A") (via step_lock_b and step_lock_a_and_transfer). The discrepancy in lock ordering causes conflicting ownership recorded in the shared _locks map when two transfers are interleaved.

## Failure Mechanism
Concrete interleaving that exposes the bug: interleaved_transfers calls lock_ab (the A→B lock step) which runs acquire("A") and sets _locks['A']=True. Next it calls lock_ba (the B→A lock step) which runs acquire("B") and sets _locks['B']=True. Then do_ab (the A→B second step) runs and calls acquire("B") — since _locks['B'] is already True the acquire function raises RuntimeError("deadlock: B already locked"). That RuntimeError is raised precisely because make_transfer_b_to_a_steps locked B before A, creating a circular wait between the two transfers recorded in _locks and detected by acquire. The variable involved is _locks and the failing function is acquire when called with resource "B" inside do_ab.

## Broken Invariant
All transfer routines must acquire locks in a single, consistent global order (testable invariant: every transfer must call acquire("A") before acquire("B")). Currently make_transfer_b_to_a_steps violates this invariant by calling acquire("B") before acquire("A")). A concrete test: after reset(), acquiring the first lock step of an A→B transfer and the first lock step of a B→A transfer in either order must not produce a state where both A and B are locked by different transfers simultaneously and a subsequent acquire raises RuntimeError; this is violated by the current implementation.

## Fix Strategy
I changed make_transfer_b_to_a_steps to acquire the same lock order as make_transfer_a_to_b_steps (A then B). By making both transfers acquire "A" before "B", we eliminate the possibility of a circular wait over the two resources recorded in _locks. The code change replaces the original step_lock_b / step_lock_a_and_transfer pair with step_lock_a / step_lock_b_and_transfer that mirror the A→B implementation but perform the B→A balance update; as a result the global lock ordering invariant (acquire "A" then "B") holds and the circular-wait deadlock scenario in the failure_mechanism cannot occur.
