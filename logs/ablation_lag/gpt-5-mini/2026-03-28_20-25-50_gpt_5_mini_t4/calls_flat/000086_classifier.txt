# Developer's Reasoning

## Root Cause
The bug is in retry_send: it uses the local variable result (the return value of send) but the control flow is inverted. The loop does `if not result: continue` and otherwise does nothing, so when send succeeds (result is True) the loop does not break or return and continues to the next iteration, causing additional calls to send. In short, retry_send fails to stop retrying on success because it never breaks or returns when result is True.

## Failure Mechanism
Given send always returns True and appends the message to the module list _sent, calling retry_send('m', max_retries=3) will call send three times. Concretely: reset(); retry_send('m', max_retries=3) -> _sent becomes ['m','m','m'] because the first successful send did not terminate the retry loop and subsequent iterations invoked send again.

## Broken Invariant
retry_send(msg, max_retries=N) must append msg at most once when the first call to send(msg) returns True. Testable statement: after reset(); retry_send('x', max_retries=5); len(get_sent()) == 1.

## Fix Strategy
Change retry_send to stop retrying as soon as send returns True and to return True on the first successful send; only continue retrying when a call to send fails (returns a falsey value). Also implement clear_log to actually clear the internal log by calling reset(). These changes ensure successful sends are not duplicated by additional retry iterations.

    """Send with retry.
