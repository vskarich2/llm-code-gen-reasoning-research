# Developer's Reasoning

## Root Cause
In pipeline.pipeline the variable raw_stats is computed by calling compute_raw_stats(normalized) (pipeline.py, line with comment '# Stage 1: raw stats'). The compute_raw_stats function in metrics.py is designed to receive the original untransformed data, but the pipeline passes the already-normalized data instead, so raw metrics are computed on transformed values rather than the original inputs.

## Failure Mechanism
For example, given input data = [10, 20, 30], normalize(data) returns [0.0, 0.5, 1.0]. The pipeline currently calls compute_raw_stats(normalized), which yields {'raw_max': 1.0, 'raw_min': 0.0, 'raw_sum': 1.5, 'raw_count': 3}. The expected raw stats for the original data are {'raw_max': 30, 'raw_min': 10, 'raw_sum': 60, 'raw_count': 3}. Because raw_stats are wrong, compute_derived(raw_stats) (raw_mean) and any consumers expecting original-scale metrics will be incorrect; downstream display (summarize_for_display) still uses cleaned values, so reports mix original-scale 'raw_*' keys that are actually normalized-scale numbers, violating the pipeline contract and producing misleading reports.

## Broken Invariant
The pipeline must satisfy: raw_stats == compute_raw_stats(data) where 'data' is the original untransformed input. Concretely: raw_stats['raw_max'] == max(data), raw_stats['raw_min'] == min(data), raw_stats['raw_sum'] == sum(data), and raw_stats['raw_count'] == len(data). Currently raw_stats are computed from normalized instead of original data, so this invariant is violated.

## Fix Strategy
Change the pipeline to pass the original 'data' into compute_raw_stats instead of the normalized variable. This restores the contract that compute_raw_stats receives untransformed input. No changes to metrics.py or transforms.py are required because compute_raw_stats already implements the correct behavior for raw (untransformed) data. The fix is a single-line change in pipeline.py: raw_stats = compute_raw_stats(data).
