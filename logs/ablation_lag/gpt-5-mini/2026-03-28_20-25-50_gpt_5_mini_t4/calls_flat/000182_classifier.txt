# Developer's Reasoning

## Root Cause
In reducers.stage and reducers.commit the same data flow was being duplicated: stage(st, processed) wrote the processed entries into st['pending'] and also built st['view'] (via project), then commit(st) copied pending into st['stable'] and freeze_view(st) (when used) would rebuild st['view'] from st['stable']. Meanwhile pipeline.process_batch and process_incremental did not call commit, leaving st['stable'] empty. Concretely, stage populated st['view'] but never st['stable'], and pipeline omitted commit(), so materialize(st) returned items from st['stable'] which stayed empty.

## Failure Mechanism
Given a new batch, process_batch calls stage(st, merged) which sets st['pending'] and st['view'] (but does not set st['stable']). Because pipeline.py omitted commit(), st['stable'] remained [], materialize(st) returned {'items': [], 'display': <view_from_pending>, 'v': <version>}. get_committed_total(st) checks st['meta']['frozen'] and returned None (falsey) so ingest(...) produced total = None even though view showed data. In short: data appeared in the display but never reached st['stable'] and commit-related metadata (frozen/version) was never updated.

## Broken Invariant
After processing a batch or incremental update (process_batch or process_incremental) the state's stable data must contain the merged entries, the view must reflect those stable entries, and st['meta']['frozen'] must be True with st['meta']['version'] incremented. Formally: calling process_batch(entries) should result in st['stable'] == merged(normalize(entries)) and get_committed_total(st) != None.

## Fix Strategy
Make stage only place processed data into st['pending'] (no view building, no version bump). Move view construction and version/frozen updates into commit, which copies pending -> stable and sets st['view'] = project(st['stable']) and increments st['meta']['version'] and sets frozen True. Ensure pipeline.process_batch and process_incremental call commit after stage so stable/view/metadata are updated. For preview (which should not commit), compute the display directly from the merged entries using project(merged) instead of relying on stage to mutate st['view']. These changes ensure a single authoritative point (commit) performs the stable write and view projection, removing duplication and restoring the invariant that materialize reads from stable.

def normalize(entries):
    seen = set()
    out = []
    for e in entries:
        k = e["id"]
        if k not in seen:
            seen.add(k)
            out.append(e)
    return out


def project(entries):
    return [{"id": e["id"], "label": e.get("label", ""), "val": e.get("val", 0)} for e in entries]


def collapse(entries):
    merged = {}
    for e in entries:
        k = e["id"]
        if k in merged:
            merged[k]["val"] = merged[k]["val"] + e.get("val", 0)
        else:
            merged[k] = dict(e)
    return list(merged.values())


def stage(st, processed):
    # stage only updates the pending slot
    st["pending"] = list(processed)


def commit(st):
    # commit copies pending -> stable and builds the view from stable
    st["stable"] = list(st["pending"])
    st["view"] = project(st["stable"])
    st["meta"]["frozen"] = True
    st["meta"]["version"] += 1


def materialize(st):
    return {
        "items": list(st["stable"]),
        "display": list(st["view"]),
        "v": st["meta"]["version"],
    }
