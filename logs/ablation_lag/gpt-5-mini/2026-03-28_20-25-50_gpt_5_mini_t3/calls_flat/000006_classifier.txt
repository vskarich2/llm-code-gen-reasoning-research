# Developer's Reasoning

## Root Cause
In config.create_config, the code does `config = DEFAULTS`, so create_config returns a reference to the global DEFAULTS dict instead of a new dict. As a result, callers that mutate the returned dict (e.g. app.apply_overrides calling settings.update(...)) end up mutating DEFAULTS itself.

## Failure Mechanism
Sequence that demonstrates the failure: 1) app.get_settings() calls create_config(), which assigns config = DEFAULTS and returns that dict object. 2) app.apply_overrides(overrides) obtains the cached settings and calls settings.update(overrides); because settings is the same object as DEFAULTS, DEFAULTS is mutated. 3) app.clear_cache() sets _cached_settings = None. 4) app.get_settings() calls create_config() again, which returns DEFAULTS — but DEFAULTS was mutated in step 2, so the newly created settings reflect the prior runtime overrides (stale/mutated defaults). The specific lines implicated are `config = DEFAULTS` in create_config and `settings.update(overrides)` in app.apply_overrides.

## Broken Invariant
create_config must return a new dict whose contents initially equal DEFAULTS, and updates to the returned dict must not mutate the module-level DEFAULTS. Concretely, after c = create_config(); c.update({'debug': True}), the expression DEFAULTS['debug'] must still be False.

## Fix Strategy
Change create_config to return a shallow copy of DEFAULTS (config = dict(DEFAULTS)) and then apply overrides into that copy. This makes the returned config independent of DEFAULTS, so app.apply_overrides will not mutate DEFAULTS and clear_cache()/get_settings() will produce fresh configs based on the unmodified DEFAULTS.
