## Root Cause
In retry_send (in code_snippets_v2/retry_dup_a/sender.py) the boolean returned from send() is stored in the variable named result and the control flow is inverted: the code uses `if not result: continue`. That means a failing send causes an immediate retry, but a successful send does not break out of the loop. As a result, when send() returns True on the first attempt the function continues iterating and calls send() again, causing duplicate deliveries to the module-level list _sent.

## Failure Mechanism
Concrete scenario: with default max_retries=2 and send always returning True, retry_send('hello') executes as follows: attempt 0 calls send('hello') which appends 'hello' to _sent and returns True. The condition `if not result` evaluates to False, so the loop body falls through and the for-loop proceeds to the next iteration; attempt 1 then calls send('hello') again and appends a second 'hello' to _sent. retry_send then returns True having sent the message twice. Thus a single logical send triggers multiple physical sends when the first attempt succeeded.

## Broken Invariant
If the first call to send(msg) succeeds (returns a truthy value), retry_send(msg, max_retries=N) must call send exactly once. This is testable: after reset(); retry_send('x', max_retries=3) the call get_sent() must return ['x'] (not multiple copies). The original code violates this invariant.

I also clarified the loop by iterating attempts from 1..max_retries for readability and returning False only if all attempts fail. I also implemented clear_log() to call reset() so the module has a single clear operation for tests and display.
