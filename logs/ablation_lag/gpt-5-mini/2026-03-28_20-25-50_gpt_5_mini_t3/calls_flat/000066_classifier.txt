As a result the loop updates the metrics counter via increment(item['value']) for every item, but emit_event is only called once after the loop using the loop variable item (which refers to the last iterated element). Additionally, processor.py defines a reset() that assigns to _counter and _events local globals that do not exist in that module, rather than calling the metrics.reset() function in metrics.py, so resetting via processor.reset() does not reset the metrics module state.

## Failure Mechanism
Given items = [{'id': 'a', 'value': 1}, {'id': 'b', 'value': 2}, {'id': 'c', 'value': 3}], process_batch runs the for-loop and calls increment(1), increment(2), increment(3) — updating metrics._counter to 6. Because emit_event(...) was placed after the loop it is invoked once with item equal to the last element {'id': 'c', 'value': 3}, appending exactly one event for item 'c' (with counter 6). The events list therefore has length 1 while the counter reflects three increments. Separately, calling processor.reset() assigns to non-existent local names _counter and _events in processor.py and does not affect metrics._counter and metrics._events, leaving the metrics module state uncleared and causing further mismatch between processed items and events.

## Broken Invariant

This invariant is violated because emit_event is called only once after the loop and processor.reset() does not clear metrics state.
