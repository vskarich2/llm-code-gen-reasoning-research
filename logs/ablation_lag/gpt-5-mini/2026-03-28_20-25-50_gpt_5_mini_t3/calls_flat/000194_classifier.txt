# Developer's Reasoning

## Root Cause
In transfer_service.execute_transfer the function interleaves balance mutations (sender.balance) and observability calls (ledger.record_debit, audit.emit_failure_alert). Specifically, the code subtracts from sender.balance and calls record_debit, then (probabilistically) raises RuntimeError before incrementing receiver.balance. The direct causal relationship is: execute_transfer modifies sender.balance (sender.balance -= amount) and calls record_debit(sender.account_id, amount) before the random failure check, so when the RuntimeError is raised the debit has been applied but the credit has not.

## Failure Mechanism
Concrete scenario: call execute_transfer(sender, receiver, 50). validate_transfer passes. record_transfer_attempt is recorded. The function then executes sender.balance -= 50 and calls record_debit(sender.account_id, 50). If random.random() < 0.3, emit_failure_alert(...) is invoked and RuntimeError('transient failure during credit') is raised. Because the exception happens before receiver.balance += 50 and before record_credit, the sender has lost 50 while the receiver was not credited and no credit ledger entry exists. That leaves account balances and ledger entries inconsistent.

## Broken Invariant
For any call execute_transfer(sender, receiver, amount), either both account balances are updated by amount (sender.balance decreased by amount and receiver.balance increased by amount) or neither account balance is changed. (Equivalently: the transfer must not leave sender.balance decreased without a corresponding increase of receiver.balance.)

## Fix Strategy
I separated pure business logic (balance mutation) into a small helper _apply_transfer and moved all observability (ledger and audit) calls into the execute_transfer wrapper. Crucially, the probabilistic transient failure is now checked before any balance changes are applied, so _apply_transfer either runs to completion updating both accounts or is never invoked. This prevents the previous partial-update path where sender.balance was decremented but receiver.balance was not. By centralizing observability in the wrapper (record_transfer_attempt, record_debit, record_credit, emit_failure_alert, emit_transfer_event) and keeping _apply_transfer as a pure state-change helper, the code is easier to reason about and the previous partial-transfer mechanism is eliminated.

```python
import random
from models import Account
from ledger import record_debit, record_credit, record_transfer_attempt
from audit import emit_transfer_event, emit_failure_alert


def validate_transfer(sender, amount):
    if amount <= 0:
        raise ValueError("amount must be positive")
    if sender.balance < amount:
        raise ValueError("insufficient funds")


def _apply_transfer(sender, receiver, amount):
    """Pure business logic: perform the balance mutation atomically."""
    sender.balance -= amount
    receiver.balance += amount


def execute_transfer(sender, receiver, amount):
    validate_transfer(sender, amount)

    # Observability: record that an attempt was made
    record_transfer_attempt(sender.account_id, receiver.account_id, amount)

    # Simulate a transient failure BEFORE applying any state changes so we
    # never leave the system in a partially-applied state.
    if random.random() < 0.3:
        emit_failure_alert(
            sender.account_id, receiver.account_id, amount,
            "connection reset during credit phase",
        )
        raise RuntimeError("transient failure during credit")

    # Core transfer: pure balance updates
    _apply_transfer(sender, receiver, amount)

    # Observability: record what actually happened
    record_debit(sender.account_id, amount)
    record_credit(receiver.account_id, amount)

    emit_transfer_event(sender.account_id, receiver.account_id, amount)

```
