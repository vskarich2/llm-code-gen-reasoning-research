# Developer's Reasoning

## Root Cause
reducers.stage only populated st['pending'] and st['view'], while reducers.commit duplicated the data by copying st['pending'] into st['stable'] and setting st['meta']['frozen']. Additionally, reducers.freeze_view rebuilt st['view'] from st['stable']. The codebase relied on both stage and commit/freeze_view to produce a committed, frozen stable state and a view, causing duplicate copies and separate steps to reach the same state.

## Failure Mechanism
In the current code path, pipeline.process_batch/process_incremental call stage(st, merged) which sets st['pending'] and st['view'] but does not set st['stable'] nor st['meta']['frozen']. Because commit() is the function that would set st['stable'] and freeze the state, failing to perform that step means st['meta']['frozen'] remains False. The selector get_committed_total checks st['meta']['frozen'] and returns None when it's False. Concretely: ingest(entries) -> process_batch(entries) -> stage sets pending/view but not stable/frozen -> back in api.ingest get_committed_total(st) returns None (instead of the numeric total) since st['meta']['frozen'] is still False. This is a concrete symptom of the redundant two-step copying not being unified into one authoritative state transition.

## Broken Invariant
After processing a batch or incremental update (i.e., after process_batch or process_incremental returns), st['meta']['frozen'] must be True and st['stable'] must contain the committed items whose display is exposed via st['view'] (equivalently, st['view'] == project(st['stable']) and st['stable'] == st['pending']). The existing pipeline violated this: process_batch returned states where st['meta']['frozen'] was False and st['stable'] was stale/empty.

## Fix Strategy
Make stage the single authoritative step that both stages and commits the processed items: set st['pending'] and st['stable'] to the processed list, build st['view'] once from the processed list, increment st['meta']['version'], and set st['meta']['frozen'] = True. This removes the need to call commit() and freeze_view() separately, eliminating the redundant copy (pending -> stable) and the redundant rebuild of view. Code changes: reducers.stage now writes stable and sets frozen; commit() and freeze_view() were removed; pipeline imports were updated to stop expecting commit/freeze_view. With this change, ingest/update will observe a frozen state and get_committed_total will return the numeric total as intended.

def normalize(entries):
    seen = set()
    out = []
    for e in entries:
        k = e["id"]
        if k not in seen:
            seen.add(k)
            out.append(e)
    return out


def project(entries):
    return [{"id": e["id"], "label": e.get("label", ""), "val": e.get("val", 0)} for e in entries]


def collapse(entries):
    merged = {}
    for e in entries:
        k = e["id"]
        if k in merged:
            merged[k]["val"] = merged[k]["val"] + e.get("val", 0)
        else:
            merged[k] = dict(e)
    return list(merged.values())


def stage(st, processed):
    # Single authoritative step: set pending and stable, build the view, bump version and mark frozen
    st["pending"] = list(processed)
    st["stable"] = list(processed)
    st["view"] = project(processed)
    st["meta"]["version"] += 1
    st["meta"]["frozen"] = True


def materialize(st):
    return {
        "items": list(st["stable"]),
        "display": list(st["view"]),
        "v": st["meta"]["version"],
    }


from state import make_state, copy_state
from reducers import normalize, collapse, stage, materialize, project


def process_batch(entries):
    st = make_state(entries)
    raw = st["raw"]

    # dedupe

    # merge values for same id

    # stage now also commits and builds the view in one step

    out = materialize(st)
    return st, out


def process_incremental(prev_state, new_entries):

    combined = st["stable"] + new_entries

    merged = collapse(cleaned)

    stage(st, merged)

    out = materialize(st)
    return st, out
