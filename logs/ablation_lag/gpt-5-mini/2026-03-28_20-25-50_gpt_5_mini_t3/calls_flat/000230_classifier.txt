# Developer's Reasoning

## Root Cause
make_transfer_b_to_a_steps uses the opposite lock acquisition order from make_transfer_a_to_b_steps: make_transfer_a_to_b_steps first acquires 'A' then 'B', while make_transfer_b_to_a_steps first acquires 'B' then 'A'. This inconsistent ordering of acquire(resource) calls causes competing transfers to each hold one lock and then call acquire on the other's held resource, which triggers acquire to raise RuntimeError when _locks[resource] is already True.

## Failure Mechanism
In interleaved_transfers the code builds steps (lock_ab, do_ab) from make_transfer_a_to_b_steps and (lock_ba, do_ba) from make_transfer_b_to_a_steps and then runs run_steps([(lock_ab,()), (lock_ba,()), (do_ab,()), (do_ba,())]). Concretely: lock_ab() calls acquire('A') and sets _locks['A']=True; lock_ba() calls acquire('B') and sets _locks['B']=True; do_ab() then calls acquire('B') — but _locks['B'] is True, so acquire raises RuntimeError('deadlock: B already locked'). The code path and variables are exactly: make_transfer_a_to_b_steps -> step_lock_a -> acquire('A'); make_transfer_b_to_a_steps -> step_lock_b -> acquire('B'); then step_lock_b_and_transfer in A→B calls acquire('B') and hits the exception on _locks.

## Broken Invariant
For any interleaving of step functions produced by make_transfer_a_to_b_steps(amount) and make_transfer_b_to_a_steps(amount) executed via run_steps, no call to acquire(resource) should encounter _locks[resource] == True. Equivalently: running any sequence of the step callables returned by the two make_transfer_* functions must never raise RuntimeError('deadlock: <resource> already locked').

## Fix Strategy
Make both transfer implementations acquire and release the needed locks atomically within a single step and use a consistent global order for acquiring multiple locks. I changed both make_transfer_a_to_b_steps and make_transfer_b_to_a_steps so the first returned step acquires both resources in a deterministic order (('A','B')), performs the state update, releases both locks, and returns the transfer result. The second returned step becomes a no-op. Because locks are held only during one step (no other step runs while a step is executing in run_steps), no other step will ever call acquire on a resource while it is held, so acquire will never see _locks[resource] == True and the RuntimeError deadlock condition cannot occur under any interleaving. The change is implemented by replacing the two-step lock-then-lock pattern (which used opposite orders) with an atomic acquire-both -> transfer -> release-both pattern for both transfers.
