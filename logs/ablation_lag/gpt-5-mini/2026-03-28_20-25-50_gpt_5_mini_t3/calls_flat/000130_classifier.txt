# Developer's Reasoning

## Root Cause
In auth.authorize, the local variable 'role' (ctx['role']) is compared against explicit role strings but lacks a branch for 'service_account'. Because authorize only checks for 'admin', 'moderator', 'user', and 'guest', a ctx['role'] == 'service_account' falls through to the final else and is treated as an unknown role.

## Failure Mechanism
A request with request['role'] == 'service_account' passes middleware.authenticate (which returns {'role': 'service_account', 'allowed': True, ...}). authorize(request) calls authenticate(request), sees ctx['allowed'] True, sets role = ctx['role'] == 'service_account', but none of the if/elif checks match 'service_account', so execution reaches the final else that returns {'can_read': False, 'can_write': False, 'can_admin': False}. The concrete effect: service account requests are denied all permissions despite middleware marking them allowed.

## Broken Invariant
For any request where middleware.authenticate(request) returns a context with 'allowed': True and 'role' equal to a recognized role (including 'service_account'), authorize(request) must not return the all-False permission set; in particular, a 'service_account' that middleware allows must receive the intended elevated permissions instead of being treated as an unknown role.

## Fix Strategy
Added an explicit branch in auth.authorize for role == 'service_account' that grants elevated permissions (matching admin-level rights). This prevents the 'service_account' value from falling through to the unknown-role else and restores the intended behavior where middleware-allowed service accounts receive the expected permissions.
