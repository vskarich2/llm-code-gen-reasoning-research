## Root Cause
The deadlock originates in make_transfer_b_to_a_steps: its inner function step_lock_b calls acquire("B") before acquire("A"), which is the opposite lock order used by make_transfer_a_to_b_steps (which acquires "A" then "B"). The global lock state is tracked in the module-level _locks dict and enforced by acquire(), so the mismatch in acquire call order in make_transfer_b_to_a_steps causes conflicting lock acquisition sequences.

## Failure Mechanism
In interleaved_transfers(), the test runs steps in this order: (lock_ab) acquires "A" (via make_transfer_a_to_b_steps.step_lock_a), then (lock_ba) acquires "B" (via make_transfer_b_to_a_steps.step_lock_b). Next, the A→B transfer's second step calls acquire("B") while B is already held by the other transfer, and the B→A transfer would next call acquire("A") while A is held by the first transfer. Because make_transfer_b_to_a_steps originally acquired B first, the two transfers can reach a circular-wait: A held by transfer1 waiting for B, and B held by transfer2 waiting for A. acquire() detects the second acquire on an already-held resource and raises RuntimeError("deadlock: ..."), so the interleaved scenario deterministically triggers that error.

## Broken Invariant
Both transfer step sequences must acquire locks in the same global order. Concretely: for any transfer between resources "A" and "B", the sequence of acquire() calls must be identical (A then B). The current code violates this: make_transfer_a_to_b_steps calls acquire("A") then acquire("B"), while make_transfer_b_to_a_steps originally called acquire("B") then acquire("A"). This invariant is testable by observing that interleaved_transfers() must never raise RuntimeError("deadlock: ...") under any interleaving.

## Fix Strategy
I changed make_transfer_b_to_a_steps so it acquires locks in the same order as make_transfer_a_to_b_steps (acquire("A") then acquire("B")). By enforcing a consistent global lock ordering (both transfers lock A then B), the circular-wait condition is eliminated: no interleaving can produce A held by one transfer and B held by the other while each waits for the other's lock. The change is localized to make_transfer_b_to_a_steps and preserves the intended balance updates (B decremented, A incremented) while preventing the RuntimeError deadlock.
