# Developer's Reasoning

## Root Cause
In cache_writer.py there were two functions with overlapping responsibilities: refresh_user_snapshot used cache_put_if_absent(f"user:{user['id']}", user['name']) while sync_user_to_cache used cache_put(f"user:{user['id']}", user['name']). The presence of refresh_user_snapshot (which only writes when the key is absent) caused callers that intended to ensure the cache matched the DB (e.g. user_service.rename_user) to call the wrong helper and therefore not update existing cache entries.

## Failure Mechanism
Concrete scenario: user_service.rename_user(user_id, new_name) calls db.update_name(...) to change the database, then calls refresh_user_snapshot(updated). Because refresh_user_snapshot delegates to cache_put_if_absent, it does not overwrite an existing key in _store. If the user's key already exists in the cache, the cache retains the old name. Later calls to cache_reader.get_display_name(user_id) return the stale value from _store, and format_user_label returns the old display name even though the DB was updated.

## Broken Invariant
After a successful rename_user(user_id, new_name) (i.e. after the DB update returns), the cache key f"user:{user_id}" must equal the user's current name in the database. This was not guaranteed because refresh_user_snapshot used cache_put_if_absent and therefore could leave the cache stale.

## Fix Strategy
Removed the duplicate/ambiguous helper refresh_user_snapshot and consolidated behavior around the existing sync_user_to_cache which performs an unconditional cache_put. Updated all callers to use sync_user_to_cache so operations that must bring the cache into agreement with the DB (save_user, rename_user, bulk_warm_cache) now unconditionally write the user's current name to the cache. Concretely: deleted refresh_user_snapshot from cache_writer.py and replaced imports and calls to refresh_user_snapshot in user_service.py with sync_user_to_cache. This ensures rename_user and save_user always update the cached name to match the DB.
