# Developer's Reasoning

## Root Cause
The bug is in process(): when called while the module-level flag _initialized is False, process() appends an error to _log and returns False, and the existing module-level list _buffer is never used. Because process() takes the error path instead of storing the item, items submitted before init() are dropped and never processed.

## Failure Mechanism
In the broken_order() scenario, run_steps calls process('a') first. Because _initialized is False, process('a') executes the branch that does _log.append(f"error:not_init:{item}") and returns False. Since process() never saved 'a' to any buffer, when init() later runs there is nothing to flush and 'a' is never processed; the final _log contains an error entry and lacks a processed:a entry.

## Broken Invariant
For any sequence of steps containing calls to process(item) and a later call to init(), every item passed to process() must appear as a "processed:<item>" entry in the final log after shutdown. Concretely: if process(x) is invoked before init(), then after init() and shutdown() complete, get_log() must contain "processed:x" exactly once.

## Fix Strategy
Change process() so that when _initialized is False it buffers the item into the existing _buffer list instead of logging an error and returning False. Change init() to set _initialized True and then flush _buffer by calling process() for each buffered item (after _initialized is True), clearing the buffer. This preserves ordering and ensures items submitted before init() are eventually processed. The change uses the existing _buffer variable and avoids the previous error path, guaranteeing each item is processed once.
