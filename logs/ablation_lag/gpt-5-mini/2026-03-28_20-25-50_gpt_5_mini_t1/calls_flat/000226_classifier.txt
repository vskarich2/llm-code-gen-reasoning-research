# Developer's Reasoning

## Root Cause
The bug is in process() which checks the module-level flag _initialized and when False appends an error log ("error:not_init:{item}") and returns False. Because process() immediately discards items when _initialized is False, items submitted before init() are never retained for later processing.

## Failure Mechanism
When run_steps executes (process, ("a",)) before init(), process() sees _initialized == False and runs _log.append(f"error:not_init:{item}") then returns False. The item "a" is neither stored in _buffer nor processed later; subsequently calling init() only appends "init" and future process calls (like process("b")) are handled, so the final _log becomes ["error:not_init:a", "init", "processed:b", "shutdown"] instead of processing "a" after initialization.

## Broken Invariant
For every item passed to process(item) before shutdown(), the shutdown log returned by shutdown() must contain a corresponding entry "processed:{item}" (i.e., all submitted items must eventually produce a "processed:<item>" log entry, regardless of whether process() was called before or after init()).

## Fix Strategy
Instead of producing an error when _initialized is False, process() now buffers the item by appending it to the module-level _buffer. init() is changed to flush _buffer after setting _initialized and appending "init": it iterates over buffered items in FIFO order and appends "processed:{item}" for each. This ensures items submitted before init() are retained and processed in arrival order when init() runs.



# Task Description
process() runs before init() and items are lost. Fix so all items are processed regardless of arrival order.
