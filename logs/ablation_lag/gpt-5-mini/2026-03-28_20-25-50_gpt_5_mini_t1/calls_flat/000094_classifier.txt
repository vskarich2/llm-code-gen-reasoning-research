# Developer's Reasoning

## Root Cause
pipeline.ingest: the for-loop over max_pipeline_retries never breaks after a successful call to send_with_retry, so the pipeline invokes the sender more than once for the same logical ingest. Also sender.send_with_retry: it always returns True even when all attempts fail, so the pipeline cannot reliably detect failure and may continue retries or treat a failure as success. These two behaviors together cause duplicate append/notify calls.

## Failure Mechanism
Example: call ingest(msg, max_pipeline_retries=2, fail_first=True). On the first pipeline attempt, sender.send raises ConnectionError once (fail_first), send_with_retry retries and succeeds, performing append(msg) and notify(msg). Because pipeline.ingest does not break after the successful send_with_retry, it performs a second pipeline iteration and calls send_with_retry again, causing a second append(msg)/notify(msg). If transient failures interact with the inner retry behavior, the message can be stored multiple times (3-4 occurrences) depending on how many retries succeed/fail before the pipeline finally stops. Additionally, because send_with_retry previously returned True even when all inner retries failed, the pipeline could misinterpret failure as success and still proceed to record the message, hiding errors.

## Broken Invariant
A single call to ingest(msg, ...) must append and notify that message at most once (i.e., exactly one append/notify on success, zero on ultimate failure). Formally: after a successful ingest(msg), store.get_messages().count(msg) increases by exactly 1. This invariant is violated by the current code (ingest may cause multiple append/notify calls for a single logical ingest).

## Fix Strategy
1) Make sender.send_with_retry return immediately on the first successful send and raise ConnectionError when all retry attempts are exhausted. This ensures callers can distinguish success from ultimate failure. 2) In pipeline.ingest, break from the pipeline-level retry loop after a successful send_with_retry so the pipeline does not call the sender multiple times for the same logical ingest. 3) Fix pipeline.reset to call the store reset and sender reset functions instead of attempting to mutate other modules' private globals. These changes ensure a successful send is observed and the pipeline stops retrying, preventing duplicate append/notify calls.
