# Developer's Reasoning

## Root Cause
The deadlock is caused by make_transfer_b_to_a_steps acquiring locks in the opposite order from make_transfer_a_to_b_steps. make_transfer_a_to_b_steps calls acquire("A") then acquire("B"), while make_transfer_b_to_a_steps calls acquire("B") then acquire("A"). The simulated lock state is stored in the module-level dictionary _locks and acquire(resource) raises RuntimeError if _locks.get(resource) is truthy. Because the two transfer functions use inconsistent acquire order, two transfers can each hold one lock and then call acquire on the other's held resource, triggering the RuntimeError (simulating a deadlock).

## Failure Mechanism
In interleaved_transfers(), the sequence is: (lock_ab) -> acquire("A") sets _locks['A']=True; (lock_ba) -> acquire("B") sets _locks['B']=True; then (do_ab) calls acquire("B") but _locks.get('B') is True so acquire raises RuntimeError('deadlock: B already locked'). The concrete cause is the reversed lock acquisition order in make_transfer_b_to_a_steps, which allows both transfers to hold different locks and then try to acquire the other's lock, producing the RuntimeError at that point.

## Broken Invariant
The module must ensure a consistent global lock acquisition order for any pair of resources: for any two resources X and Y, every transfer must call acquire on that pair in the same relative order (e.g., alphabetical). Currently this is violated because make_transfer_a_to_b_steps acquires ("A","B") while make_transfer_b_to_a_steps acquires ("B","A"). A concrete, testable statement of the invariant: for any interleaving of the step functions produced by make_transfer_a_to_b_steps and make_transfer_b_to_a_steps, run_steps should not reach a state where one transfer holds resource X and another holds resource Y with each then calling acquire on the other's held resource (i.e., the code should not allow the two-lock-held deadlock pattern).

## Fix Strategy
I enforce a canonical/global ordering of resources when acquiring locks. I added a small ordering step so both transfer factories acquire locks in the same order (sorted resource names). That removes the possibility that two concurrent transfers will each hold a different lock and then attempt to acquire the other's lock, eliminating the two-lock circular wait deadlock. The change is localized: both make_transfer_a_to_b_steps and make_transfer_b_to_a_steps determine first_lock, second_lock = sorted([src, dst]) and then acquire the locks in that fixed order before performing the state mutation; the transfer direction still updates _state appropriately.

    """Simulate lock. Raises RuntimeError if already held (deadlock)."""

    _locks[resource] = True


def release(resource):
    _locks[resource] = False

    return dict(_state)

    results = []
    for fn, args in steps:
        results.append(fn(*args))
    return results

    """Transfer A→B: acquire locks in canonical order, then transfer."""
    # enforce canonical ordering so all transfers acquire locks in the same order
    first_lock, second_lock = sorted(["A", "B"])

    def step_lock_first():
        acquire(first_lock)
        return f"locked_{first_lock}"

    def step_lock_second_and_transfer():
        acquire(second_lock)
        # perform transfer directionally (A -> B)
        _state["A"] -= amount
        _state["B"] += amount
        # release both locks
        release(second_lock)
        release(first_lock)
        return "transferred_a_to_b"
