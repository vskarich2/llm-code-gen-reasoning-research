## Root Cause
In pipeline.find_best the function relies on the module-level variable _last_best and the else branch at the end of the search sets best = _last_best. Specifically, the line "else:\n        best = _last_best" causes the function to reuse a previously-stored record from _last_best rather than returning None when no current record passes the threshold.

## Failure Mechanism
If a prior call to find_best found a record and set _last_best, then a later call with records where none exceed threshold will hit the for/else else-branch and assign best = _last_best (the prior record). That returns stale data to callers that expect None for 'no match', causing downstream processing to operate on an incorrect record and potentially crash. The problematic code path is the else clause that reuses _last_best instead of clearing it or returning None.

## Broken Invariant

Concrete testable statement: for any records list in which no record has value > 50, find_best(records, rules) must return None. The existing implementation can return a non-None _last_best instead, violating this invariant.

## Fix Strategy

Additionally, the reset() function previously attempted to clear loader state by creating local module-level _loaded/_load_status variables; instead call loader.reset() to clear the loader module's actual state. These changes ensure find_best never returns a stale _last_best and reset actually clears loader state.
