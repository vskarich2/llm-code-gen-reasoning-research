# Developer's Reasoning

## Root Cause
The pipeline relied on three separate reducer functions—stage(), commit(), and freeze_view()—that duplicated and scattered the single logical operation of making merged entries become the committed/display state. Specifically, stage(st, processed) assigns st['pending'] = processed and st['view'] = project(processed), while commit(st) then copies st['pending'] into st['stable'] (st['stable'] = list(st['pending'])) and freeze_view(st) recomputes st['view'] = project(st['stable']). This causes the same data to be copied and rebuilt across stage(), commit(), and freeze_view(), producing redundant state mutations on st['pending'], st['stable'], and st['view'].

## Failure Mechanism
Because stage() already builds the presentation (st['view']) and commit() copies pending into stable, freeze_view() simply repeats the projection. In the original flow, pipeline.process_batch/process_incremental used stage() but intentionally omitted commit()/freeze_view(), leaving st['stable'] empty and st['meta']['frozen'] False while st['view'] held the merged result. That created an inconsistent observable behavior: get_display_items(st) returned the merged view but get_committed_total(st) returned None since meta['frozen'] remained False and st['stable'] was not updated. Concretely, a call to ingest(entries) produced a materialized['display'] but total was None because the pipeline never consolidated staged data into stable state; the duplication and split responsibilities across stage/commit/freeze_view made it easy to forget the necessary step and caused this inconsistent contract.

## Broken Invariant
After processing a batch or incremental update, the state must satisfy: st['stable'] must equal the merged (collapse(normalize(...))) result, st['view'] must equal project(st['stable']), and st['meta']['frozen'] must be True while st['meta']['version'] has been incremented by one. This invariant is testable by checking equality between collapse(normalize(...)) and st['stable'], equality between project(st['stable']) and st['view'], and that get_committed_total(st) returns a numeric total rather than None.

## Fix Strategy
I removed the redundant freeze_view/commit/stage split and centralized the commit step inside the pipeline: process_batch and process_incremental now set st['pending'], st['stable'], and st['view'] from the merged result in one place and update meta (increment version and set frozen True). This ensures the invariant (stable/view/frozen/version) holds immediately after processing and eliminates the duplicated copying and rebuilding across functions. preview() was updated to compute a transient view without committing (so previews don't set st['stable'] or meta['frozen']). I also removed the unused reducer functions (stage, commit, freeze_view) from reducers.py so callers can't accidentally use the old, inconsistent multi-step flow.

def normalize(entries):
    seen = set()
    out = []
    for e in entries:
        k = e["id"]
        if k not in seen:
            seen.add(k)
            out.append(e)
    return out


def project(entries):
    return [{"id": e["id"], "label": e.get("label", ""), "val": e.get("val", 0)} for e in entries]


def collapse(entries):
    merged = {}
    for e in entries:
        k = e["id"]
        if k in merged:
            merged[k]["val"] = merged[k]["val"] + e.get("val", 0)
        else:
            merged[k] = dict(e)
    return list(merged.values())


def materialize(st):
    return {
        "items": list(st["stable"]),
        "display": list(st["view"]),
        "v": st["meta"]["version"],
    }
