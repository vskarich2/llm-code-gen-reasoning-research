# Developer's Reasoning

## Root Cause
In processor.process_batch the call to emit_event was placed outside the for loop and used the loop variable 'item' after the loop completed. As written, only the final 'item' from the iteration is referenced and a single event is appended. Additionally, processor.reset attempted to reinitialize module-level variables '_counter' and '_events' that are defined in metrics.py, not in this module, which is incorrect.

## Failure Mechanism
Given items = [{"id": 1, "value": 2}, {"id": 2, "value": 3}], process_batch first calls increment for each item, so metrics._counter increases by 5. Because emit_event was executed only once after the loop, metrics._events receives a single event for item id 2. The observable effect is that the counter reflects both items' values (5) but the events list length increases by 1 instead of 2, causing event counts to not match items processed.

## Broken Invariant
For any call to process_batch(items), the metrics module must have exactly len(items) new events appended, and for each index i in 0..len(items)-1 the i-th newly appended event must have 'item_id' == items[i]['id']. Formally: before = len(get_events()); process_batch(items); after = len(get_events()); after - before == len(items) AND for j in range(len(items)): get_events()[before + j]['item_id'] == items[j]['id'].

## Fix Strategy
I moved the emit_event call inside the per-item loop so emit_event is invoked once for each item immediately after increment(item['value']). This directly restores the one-event-per-item contract. I also fixed reset() to call the metrics.reset function (imported as metrics_reset) instead of attempting to mutate undefined globals in this module. These changes ensure each processed item produces one event and that reset correctly clears the shared metrics state.
