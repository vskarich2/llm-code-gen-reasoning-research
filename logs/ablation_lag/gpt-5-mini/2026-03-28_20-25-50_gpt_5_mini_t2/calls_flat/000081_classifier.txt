## Root Cause
In pipeline.find_best, the function relies on the module variable _last_best when no record in the current valid list exceeds the threshold. Specifically, the for-loop which searches for a record > threshold never initializes a local 'best' variable before the loop, and the else branch assigns best = _last_best. As a result, _last_best (a value from a previous invocation) is reused instead of returning None when there is no current qualifying record.

## Failure Mechanism
Example: First call to find_best(records1, rules) finds a record R1 with R1['value'] > 50 and sets _last_best = R1. Later, a second call find_best(records2, rules) has no record with value > 50. The loop body never sets a new 'best', so the else branch executes and assigns best = _last_best (still R1). The function returns R1 even though no record in the current input qualifies. Code that expects None when no match exists may then operate on this stale record, causing incorrect results or runtime errors in downstream processing.

## Broken Invariant
Contract violated by pipeline.find_best: For any invocation where no record in the provided 'records' both passes the validation rules and has 'value' > threshold, find_best must return None and must not return data from a prior call. Formally, if all(rec['value'] <= threshold or rec not in validated set for rec in records) then find_best(records, rules) is None and _last_best is None.

## Fix Strategy
Change find_best to explicitly initialize 'best = None' and to clear _last_best when no current record exceeds the threshold. This prevents reuse of stale data: when no candidate is found, _last_best is set to None and the function returns None. The _pipeline_result is set based on the (now correctly determined) best value. No other modules changed.
