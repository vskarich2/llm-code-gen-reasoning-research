# Developer's Reasoning

## Root Cause
The bug is in limiter.should_allow: the boolean expression uses 'expired', 'under_limit', and 'exempt' but is written as 'not expired and under_limit or exempt'. Because Python's operator precedence evaluates 'and' before 'or', the expression effectively becomes '((not expired) and under_limit) or exempt', so the variable 'exempt' can force a True return even when 'expired' is True.

## Failure Mechanism
Consequence in code: when is_expired(timestamp, now, window_seconds) sets expired=True and is_exempt(client_id, exempt_list) sets exempt=True, the return value computes as (False and under_limit) or True => True, so should_allow returns True and an expired token is allowed. Concretely, a request with state['first_seen'] older than window_seconds (expired=True) from a client in EXEMPT_CLIENTS (exempt=True) will be allowed, violating the intended policy that expired tokens are always rejected.

## Broken Invariant
Invariant violated: For any input, if is_expired(timestamp, now, window_seconds) returns True, then should_allow(...) must return False. This is testable: when expired=True, should_allow should never return True regardless of count, limit, or exempt_list membership.

## Fix Strategy
I fixed the boolean grouping in limiter.should_allow so the function returns (not expired) and (under_limit or exempt). This enforces that expired must be False before any exemption or under-limit status can allow a request. The change prevents 'exempt' from overriding an expired token by applying the 'not expired' check to the whole (under_limit or exempt) clause.

def should_allow(client_id, count, limit, timestamp, now,
                 window_seconds, exempt_list):
    """Decide whether to allow a request.

    Allow if:
      - token is not expired AND (under limit OR exempt)

    Exempt clients bypass the rate limit even if over it,
    but expired tokens are always rejected.
    """

    # Ensure expired tokens are always rejected by grouping correctly.
