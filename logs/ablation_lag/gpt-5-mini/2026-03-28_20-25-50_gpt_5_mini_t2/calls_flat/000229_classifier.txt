# Developer's Reasoning

## Root Cause
make_transfer_b_to_a_steps acquires locks in the opposite order from make_transfer_a_to_b_steps (it calls acquire("B") first, then acquire("A")). The global _locks mapping and acquire() raise RuntimeError when a resource is already held, so the inconsistent lock ordering between make_transfer_a_to_b_steps and make_transfer_b_to_a_steps allows the sequence of calls in interleaved_transfers to hit acquire on an already-locked resource.

## Failure Mechanism
In interleaved_transfers() the steps are run as: lock_ab (acquires "A"), lock_ba (acquires "B"), do_ab (attempts acquire("B")). Because lock_ba already acquired "B", calling acquire("B") in do_ab raises RuntimeError("deadlock: B already locked"). Concretely: make_transfer_a_to_b_steps.step_lock_a sets _locks['A']=True; make_transfer_b_to_a_steps.step_lock_b sets _locks['B']=True; then make_transfer_a_to_b_steps.step_lock_b_and_transfer calls acquire('B') and errors because _locks['B'] is true. The inconsistent ordering of acquires (A then B vs B then A) is the direct cause of the runtime error.

## Broken Invariant
All transfers must acquire resources in a consistent global order so that no interleaving of the provided step functions leads to acquire(...) being called on a resource already held by another transfer. Equivalently, calling interleaved_transfers() must not return an error dict — i.e., no RuntimeError("deadlock: ...") should be raised for the provided interleaving.

## Fix Strategy
Change both transfer helpers so the first 'lock' step is only a preparation/no-op and the actual locking happens in the transfer step; when acquiring locks in the transfer step, always acquire the two resource names in a canonical (sorted) order and release in the reverse order. This enforces a consistent global lock order (sorted resource names) regardless of transfer direction and prevents the lock-ordering deadlock. Concretely, make_transfer_a_to_b_steps and make_transfer_b_to_a_steps now have the transfer step acquire sorted(["A","B"]) before mutating _state and then release in reverse; the initial 'lock' step no longer calls acquire, avoiding the previous partial-lock interleaving that caused acquire(...) to be invoked on an already-held resource.
