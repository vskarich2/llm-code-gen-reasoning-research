## Root Cause
The function make_transfer_b_to_a_steps locks resource B first, then resource A, which is the opposite order of make_transfer_a_to_b_steps that locks A first, then B. This inconsistent lock ordering causes a deadlock when two transfers are interleaved, with one holding A and waiting for B, and the other holding B and waiting for A.

## Failure Mechanism
When interleaving transfers, the first transfer locks resource A and then attempts to lock B, while the second transfer locks resource B and then attempts to lock A. If the first transfer has locked A and the second has locked B, both will wait indefinitely for the other resource, causing a deadlock scenario, as neither can proceed to release their locks.

## Broken Invariant
The code guarantees that all transfers acquire resources in a consistent global lock order, preventing deadlocks, such that if one transfer has locked resource X, all other transfers will lock resource Y only after releasing X, ensuring no circular wait conditions occur.

## Fix Strategy
The fix involves enforcing a consistent lock acquisition order in both transfer functions. By modifying make_transfer_b_to_a_steps to acquire resource A first, then resource B, matching the order in make_transfer_a_to_b_steps, the code ensures that all transfers lock resources in the same order, preventing circular wait conditions and thus eliminating deadlocks.
