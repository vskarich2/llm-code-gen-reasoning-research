# Developer's Reasoning

## Root Cause
The client.py module captures the value of get_config() at import time by assigning it to the variable _client_config, which is initialized immediately when the module is loaded. This means that subsequent calls to get_config() do not affect _client_config, causing the client to use stale configuration data.

## Failure Mechanism
When reset_config() is called in config.py, it resets the global _config variable, but since client.py has already captured the config in _client_config during import, the client continues to use the old configuration, including the outdated timeout value, even after the reset.

## Broken Invariant
The client should always use the latest configuration returned by get_config() when calling get_db_url() and get_timeout(), reflecting any resets or updates made via reset_config().

## Fix Strategy
Changing the client.py code to call get_config() dynamically within get_db_url() and get_timeout() functions ensures that the client retrieves the current configuration each time, rather than relying on a stale, eagerly captured value. This aligns the client's behavior with the intended lazy loading and reset semantics.
