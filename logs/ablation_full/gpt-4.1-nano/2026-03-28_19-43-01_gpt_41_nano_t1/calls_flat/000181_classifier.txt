## Root Cause
In process_batch and process_incremental, the functions stage() and commit() both copy data into the state, and freeze_view() rebuilds the view that stage() already built, leading to redundant data copying and view rebuilding.

## Failure Mechanism
When process_batch or process_incremental are called, they invoke stage() to update pending and view, then later call freeze_view() which rebuilds the view from stable data, causing unnecessary recomputation and data duplication, which can lead to inefficiencies and potential inconsistencies.

## Broken Invariant
The view in the state should be consistent with the pending data after staging, and freeze_view() should not be necessary if the view is already built during staging, meaning that calling freeze_view() after stage() is redundant and can cause unnecessary overhead.

## Fix Strategy
Removing the call to freeze_view() from process_batch and process_incremental eliminates the redundant view rebuild, relying on stage() to set the view initially, thus simplifying the pipeline and maintaining the invariant that the view reflects the staged data without extra recomputation.

    # dedupe
    cleaned = normalize(raw)

    # merge values for same id

    # stage puts merged into pending + builds view from merged

def process_incremental(prev_state, new_entries):

    combined = st["stable"] + new_entries

    cleaned = normalize(combined)
    merged = collapse(cleaned)

    stage(st, merged)

    out = materialize(st)
    return st, out


def recompute_view(st):
