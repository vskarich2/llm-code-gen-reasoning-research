## Root Cause
The function should_allow in limiter.py has an incorrect operator precedence in its return statement. Specifically, it returns 'not expired and under_limit or exempt', which is parsed as '((not expired) and under_limit) or exempt'. This causes expired tokens for exempt clients to be allowed because the 'or exempt' part makes the entire expression true when exempt is True, regardless of expiration or limit status.

## Failure Mechanism
When a client has an expired token but is also in the exempt list, the current condition evaluates to True due to the 'or exempt' clause, allowing requests from expired tokens for exempt clients to pass through the rate limiter, violating the intended policy that expired tokens should always be rejected regardless of exemption status.

## Broken Invariant
The should_allow function must return False for any request with an expired token, even if the client is exempt, ensuring that expired tokens are always rejected regardless of exemption status.

## Fix Strategy
Adding parentheses around the 'not expired' and 'under_limit or exempt' expressions in the return statement in limiter.py ensures the correct logical evaluation: 'not expired and (under_limit or exempt)'. This change enforces that expired tokens are always rejected, and exemption only bypasses the limit check when tokens are valid.
