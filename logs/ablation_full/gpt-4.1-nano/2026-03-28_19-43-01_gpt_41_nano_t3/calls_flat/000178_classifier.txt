## Root Cause
In process_batch and process_incremental, the functions stage() and commit() both copy data into the state, and freeze_view() rebuilds the view that stage() already built, leading to redundant data copying and view rebuilding steps.

## Failure Mechanism
When process_batch or process_incremental are called, they invoke stage() to update the pending data and build the view, then call commit() to set stable data and freeze_view() to rebuild the view again, causing unnecessary duplication of data copying and view reconstruction, which can lead to inefficiencies and potential inconsistencies.

## Broken Invariant
The view in the state should be consistent with the pending data after staging, and calling freeze_view() after stage() is redundant because stage() already updates the view, so additional calls to freeze_view() are unnecessary and may cause performance issues.

## Fix Strategy
Removing the commit() and freeze_view() calls from process_batch and process_incremental prevents redundant copying and view rebuilding, relying solely on stage() to update the view, thus simplifying the pipeline and maintaining the correct invariant that the view reflects the latest staged data.

from reducers import normalize, collapse, stage, commit, freeze_view, materialize, project


def process_batch(entries):
    st = make_state(entries)
    raw = st["raw"]

    # dedupe
    cleaned = normalize(raw)

    # merge values for same id
    merged = collapse(cleaned)

    # stage puts merged into pending + builds view from merged
    stage(st, merged)

    # commit and freeze_view removed as redundant

    out = materialize(st)
    return st, out


def process_incremental(prev_state, new_entries):
    st = copy_state(prev_state)
    combined = st["stable"] + new_entries

    cleaned = normalize(combined)
    merged = collapse(cleaned)

    stage(st, merged)

    out = materialize(st)
    return st, out


def recompute_view(st):
    st["view"] = project(st["pending"])
    return st
