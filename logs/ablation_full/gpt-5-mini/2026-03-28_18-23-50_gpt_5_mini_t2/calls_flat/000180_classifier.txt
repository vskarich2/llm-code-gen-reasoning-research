# Developer's Reasoning

## Root Cause
The pipeline relied on three separate reducer functions—stage(), commit(), and freeze_view()—that redundantly copied the same processed data into different state slots. Specifically, reducers.stage(st, processed) already assigned processed to st['pending'] and built st['view'], while reducers.commit(st) immediately copied st['pending'] into st['stable'] and set st['meta']['frozen'] = True, and reducers.freeze_view(st) rebuilt st['view'] from st['stable']. This caused duplicated data-copy operations across stage() and commit() and an unnecessary rebuild of view in freeze_view().

## Failure Mechanism
In the current code path, process_batch() and process_incremental() call only stage(st, merged) and intentionally omitted commit() and freeze_view() (as seen in pipeline.py comments). Because commit() was the function that populated st['stable'] and set meta['frozen'] to True, after processing a batch the state left st['stable'] empty and st['meta']['frozen'] False. Consequently, selectors.get_committed_total(st) returned None (it checks meta['frozen']) even though stage() had already produced the visible view. Concretely: process_batch -> stage sets st['pending'] and st['view'], but st['stable'] remains [] and meta['frozen'] stays False (since commit wasn't called), so ingest() receives total = None unexpectedly.

## Broken Invariant
After processing a batch with process_batch() (or processing incrementally with process_incremental()), the state must have st['stable'] equal to the committed items and st['meta']['frozen'] == True so that get_committed_total(st) returns the committed total. (Testable: call process_batch([...]) then assert st['stable'] == materialize(st)['items'] and get_committed_total(st) is not None.)

## Fix Strategy
Merge the commit behavior into stage() and remove the separate commit() and freeze_view() functions to eliminate duplicated copying and redundant view rebuilding. stage() now accepts an explicit commit flag (defaulting to True for normal pipeline operations). When commit=True, stage() sets st['stable'] = processed and st['meta']['frozen'] = True in addition to updating st['pending'], st['view'], and version. For preview usage, callers can call stage(..., commit=False) to avoid committing. This keeps a single place that copies processed results into state and avoids rebuilding view from stable because stage() already constructs the view. I updated reducers.py to remove commit() and freeze_view(), adjusted imports in pipeline.py, and changed api.preview() to call stage(..., commit=False) so preview remains uncommitted.

def normalize(entries):
    seen = set()
    out = []
    for e in entries:
        k = e["id"]
        if k not in seen:
            seen.add(k)
            out.append(e)
    return out


def project(entries):
    return [{"id": e["id"], "label": e.get("label", ""), "val": e.get("val", 0)} for e in entries]


def collapse(entries):
    merged = {}
    for e in entries:
        k = e["id"]
        if k in merged:
            merged[k]["val"] = merged[k]["val"] + e.get("val", 0)
        else:
            merged[k] = dict(e)
    return list(merged.values())


def stage(st, processed, commit=True):
    """Place processed items into pending and build the view.

    If commit is True, also copy processed into stable and mark the state frozen.
    """

    st["view"] = project(processed)
    st["meta"]["version"] += 1

    if commit:
        # commit behavior merged into stage to avoid redundant copying steps
        st["stable"] = list(processed)
        st["meta"]["frozen"] = True


def materialize(st):
    return {
        "items": list(st["stable"]),
        "display": list(st["view"]),
        "v": st["meta"]["version"],
    }
