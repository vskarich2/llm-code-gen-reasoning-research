## Root Cause
service.update_record: the cache_invalidate(key) operation (removing _data[key] and _version[key]) when used immediately before cache_set(key, value) creates a redundant invalidation call that opens a race window and serves no purpose when followed by an immediate cache_set.

## Failure Mechanism
If update_record performs cache_invalidate(key) → this mutation removes the key from cache (_data.pop(key)) and its version (_version.pop(key)) → a concurrent reader between the invalidate and the subsequent cache_set sees an uncached key, reads from the database and may write a stale value back to the cache → when the original update resumes and cache_set writes the new value the timing could still produce inconsistencies in some interleavings (or, at minimum, the invalidate is unnecessary overhead). Observable failure: read_record returns stale or inconsistent values around updates, and extra invalidation causes avoidable cache churn.

## Broken Invariant
After update_record(key, value) completes, read_record(key) should return value (the newly written value) and the cache should reflect that value. This invariant can be tested by calling update_record then immediately calling read_record and expecting the new value.

## Fix Strategy
Modify service.update_record to stop invalidating the cache before setting it. Instead, after writing to the DB (db_write("records", key, value)), immediately call cache_set(key, value). This removes the redundant cache_invalidate operation and eliminates the invalidate→read→stale-write race window. The change references actual behavior: db_write commits the authoritative value, and directly calling cache_set updates the in-memory cache to that value; no explicit cache removal is needed prior to setting.
