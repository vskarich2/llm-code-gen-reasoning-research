# Developer's Reasoning

## Root Cause
make_transfer_b_to_a_steps acquires locks in the opposite order from make_transfer_a_to_b_steps. Specifically, make_transfer_a_to_b_steps calls acquire("A") then acquire("B"), while make_transfer_b_to_a_steps calls acquire("B") then acquire("A"). That opposite ordering creates a circular lock dependency between the two transfer implementations using the shared _locks state and the acquire() function.

## Failure Mechanism
In interleaved_transfers the following sequence happens: reset() clears state; lock_ab() (from make_transfer_a_to_b_steps) calls acquire("A") and sets _locks['A']=True; lock_ba() (from the buggy make_transfer_b_to_a_steps) then calls acquire("B") and sets _locks['B']=True; do_ab() then executes and calls acquire("B") but _locks.get('B') is True, so acquire(...) raises RuntimeError("deadlock: B already locked"). The opposite ordering (A then B vs B then A) is the direct cause: each transfer holds one lock and then attempts the other, producing the raised error in the simulated lock implementation.

## Broken Invariant
For transfers operating on resources 'A' and 'B', all transfer implementations must acquire the same global lock order: acquire('A') must always be called before acquire('B'). Concretely, after calling make_transfer_*_steps(amount), the first step function must call acquire('A') and the second step must call acquire('B'). This is testable by invoking the two lock-step functions and checking the order of acquire calls against the _locks state.

## Fix Strategy
I made the lock acquisition order consistent by changing make_transfer_b_to_a_steps so it acquires 'A' first and then 'B', matching make_transfer_a_to_b_steps. This removes the circular (A->B and B->A) ordering that caused the RuntimeError in the simulated acquire() implementation. Because both transfer paths now follow the same global lock ordering, there is no cycle in resource acquisition and the interleaving that previously raised "deadlock: B already locked" cannot occur. The change is local to make_transfer_b_to_a_steps and preserves the transfer semantics (subtract amount from B, add to A) while aligning lock ordering.

_state = {"A": 100, "B": 100}

    _locks.clear()

    _state["B"] = 100


def acquire(resource):
    """Simulate lock. Raises RuntimeError if already held (deadlock)."""
    if _locks.get(resource):
        raise RuntimeError(f"deadlock: {resource} already locked")
    _locks[resource] = True


def release(resource):
    _locks[resource] = False


def get_state():
    return dict(_state)


def run_steps(steps):
    results = []
    for fn, args in steps:
        results.append(fn(*args))
    return results


def make_transfer_a_to_b_steps(amount):
    """Transfer A→B: lock A first, then B."""

    def step_lock_a():
        acquire("A")
        return "locked_A"

    def step_lock_b_and_transfer():
        acquire("B")
        _state["A"] -= amount
        _state["B"] += amount
        release("B")
        release("A")
        return "transferred_a_to_b"

    return step_lock_a, step_lock_b_and_transfer


def make_transfer_b_to_a_steps(amount):
    """Transfer B→A: lock A first, then B (consistent ordering with A→B)."""

        # Acquire A first to match the global ordering used by make_transfer_a_to_b_steps
        acquire("A")
        return "locked_A"

        acquire("B")
        _state["B"] -= amount
        _state["A"] += amount
        release("B")
        release("A")
        return "transferred_b_to_a"

    return step_lock_a, step_lock_b_and_transfer


def sequential_transfers():
    """A→B then B→A. Sequential: works fine."""

    lock_ab, do_ab = make_transfer_a_to_b_steps(10)
    lock_ba, do_ba = make_transfer_b_to_a_steps(10)

        (lock_ab, ()), (do_ab, ()),
        (lock_ba, ()), (do_ba, ()),
