# Developer's Reasoning

## Root Cause
client.py top-level assignment `_client_cfg = get_config()` captures the config dictionary reference at import time; the assignment operation stores a pointer to the dict returned by config.get_config(), so subsequent calls in get_api_key()/get_base_url() read from the stale `_client_cfg` instead of the current config.

## Failure Mechanism
Call sequence: application calls config.reset_config() → config._config is set to None and a new dict will be created on next get_config() call → client._client_cfg still references the old dict object (it was captured at import-time) → get_api_key()/get_base_url() read values from the old dict → handler.make_request() and other call sites observe and return stale api_key/base_url values (observable failure: requests use old base_url or old api_key).

## Broken Invariant
Invariant: handler.make_request(endpoint) must reflect the current configuration from config.get_config() after config.reset_config() and subsequent config.set_config() calls. Testable violation: after calling config.reset_config(); config.set_config('api_key','new-key'); handler.make_request('x')['api_key'] != 'new-key' (it returns the old value).

## Fix Strategy
Remove the import-time capture of the config dict in client.py and make client API functions fetch the config from config.get_config() at call-time. Concretely: delete the module-level `_client_cfg = get_config()` and change get_api_key() and get_base_url() to call get_config() inside the function. This breaks the causal chain because after config.reset_config() the next call to get_config() will return the new dict and client functions will read the up-to-date values.
