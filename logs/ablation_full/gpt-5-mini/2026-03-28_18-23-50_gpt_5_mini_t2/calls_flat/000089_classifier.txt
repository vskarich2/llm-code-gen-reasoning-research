# Developer's Reasoning

## Root Cause
In sender.send_with_retry the function never stops after a successful call to sender.send because there is no break or return inside the try block. This causes send(msg) to be invoked repeatedly for each iteration of the for-loop. The causal variables are send_with_retry (the retry loop) and send (which calls append and notify), so the missing break/return in send_with_retry leads to multiple calls to append/notify.

## Failure Mechanism
When send_with_retry is called with max_retries > 1 and send does not raise (for example fail_first=False), the for attempt in range(max_retries) loop will call send(msg) on every iteration. Each successful send calls append(msg) and notify(msg), so the message and notification are recorded once per loop iteration. Concretely: with max_retries=3 and fail_first=False, send is called three times, appending the same message three times into store._messages and pushing three notifications into store._notifications.

## Broken Invariant
send_with_retry(msg, max_retries=N) must result in at most one stored message and at most one notification for a single logical send attempt. Specifically, after a successful send (no ConnectionError), store.message_count() increases by exactly 1 and len(get_notifications()) increases by exactly 1. The current code violates this invariant when max_retries > 1 or when the first attempts succeed, because it performs repeated successful sends.

## Fix Strategy
Return immediately after a successful call to send so the loop does not continue and duplicate append/notify. Also, if all attempts fail, re-raise the last ConnectionError to surface the transient failure to the caller. Additionally, fix reset to actually clear the shared store by delegating to store.reset() instead of creating local _messages/_notifications variables. These changes prevent multiple append/notify invocations and ensure the store is reset correctly.

            continue
