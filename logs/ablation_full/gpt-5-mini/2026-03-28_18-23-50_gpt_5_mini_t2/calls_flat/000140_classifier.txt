# Developer's Reasoning

## Root Cause
In limiter.should_allow the boolean expression uses variables 'expired', 'under_limit', and 'exempt' but omits parentheses. The return expression `not expired and under_limit or exempt` is parsed by Python as `((not expired) and under_limit) or exempt`, so the value of 'exempt' can make the whole expression True even when 'expired' is True.

## Failure Mechanism
When is_expired(timestamp, now, window_seconds) returns True (so expired=True) and is_exempt(client_id, exempt_list) returns True (exempt=True), the buggy expression evaluates as (False and under_limit) or True => True, causing should_allow to return True and allow a request with an expired token. Concretely: expired=True, under_limit=False, exempt=True => buggy result True (allowed) while the intended logic should block expired tokens.

## Broken Invariant
For any call to should_allow, if is_expired(timestamp, now, window_seconds) is True then should_allow MUST return False regardless of is_exempt(client_id, exempt_list).

## Fix Strategy
Explicitly group the boolean expression so the function requires the token to be not expired AND (either under the limit OR exempt). Changing the return to `(not expired) and (under_limit or exempt)` enforces that when expired is True the left side is False and the whole expression is False, preventing exempt clients from bypassing the expiration check.
