# Developer's Reasoning

## Root Cause
refresh_user_snapshot (cache_writer.py) calls cache_put_if_absent on key user:{user['id']} which uses the _store dict and intentionally avoids overwriting an existing entry; this causes writes that should update the cached display name to become no-ops when the key already exists.

## Failure Mechanism
rename_user (user_service.py) -> calls db.update_name(user_id, new_name) -> then calls refresh_user_snapshot(updated) -> refresh_user_snapshot executes cache_put_if_absent(f"user:{user['id']}", user['name']) -> because the key already exists in _store the put_if_absent does not replace the old value -> cache remains the old name -> cache_reader.get_display_name(user_id) returns stale name -> UI or other consumers show outdated display name.

## Broken Invariant
After persisting or updating a user's name in the database (persist_user or db.update_name), the cache entry user:{id} must equal the authoritative name stored in the DB. This is testable by: persist/update -> call sync/cache path -> assert get_display_name(id) == lookup_user(id)['name']. Currently that property can be violated when refresh_user_snapshot is used because it does not overwrite existing entries.

## Fix Strategy
Remove the duplicate helper refresh_user_snapshot and consolidate to a single authoritative function sync_user_to_cache that performs an unconditional write (cache_put) to ensure the cache reflects the current DB value after saves/renames. Update all call sites in user_service to call sync_user_to_cache. This breaks the causal chain because the former no-op path (cache_put_if_absent) is removed; after DB update the cache write will overwrite any existing value.
