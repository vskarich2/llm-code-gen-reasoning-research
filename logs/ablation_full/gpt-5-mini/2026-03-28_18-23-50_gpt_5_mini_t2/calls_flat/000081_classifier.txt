## Root Cause
In pipeline.find_best the function uses a for/else pattern that assigns best = _last_best in the else branch. That means when no current record exceeds the threshold the code reads and returns the module-level variable _last_best (set by a previous call) instead of returning None. Concretely, the local variable best is only set inside the loop when a record exceeds threshold; otherwise the else branch reuses _last_best and so find_best returns stale data.

## Failure Mechanism
Example: first call find_best([{ 'value': 100 }], rules) finds the record and sets _last_best to that record. A subsequent call with records that validate but none exceed threshold (e.g. [{ 'value': 10 }]) runs the loop without finding a match, hits the for/else branch and executes best = _last_best, returning the previous 100-value record even though no current record satisfies the threshold. The pipeline_result is set to 'found' and a caller gets stale data instead of None.

## Broken Invariant
The function pipeline.find_best(records, rules) must return either the matching record (the first valid record with value > threshold) or None when no such record exists for the provided records and rules. This invariant is violated when find_best returns a record from a prior invocation (i.e. _last_best) instead of None for inputs with no qualifying records.

## Fix Strategy
Initialize best to None and clear the remembered _last_best when the current invocation yields no qualifying record. By removing the for/else that assigns best = _last_best and instead explicitly setting _last_best = None when nothing is found, the function can no longer return stale data. The code now only updates _last_best when a fresh qualifying record is found and returns None when no record exceeds the threshold; pipeline_result is updated accordingly.
