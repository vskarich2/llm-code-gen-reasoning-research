# Developer's Reasoning

## Root Cause
The function process_batch in pipeline.py removed the calls to reducers.commit and reducers.freeze_view. As a result, st['meta']['frozen'] is never set to True (commit sets it) and st['stable'] is never populated from st['pending'] (commit copies pending -> stable). Also freeze_view, which would copy stable into st['view'], is not invoked, so st['view'] can still reflect staged/pending data rather than the canonical committed ordering.

## Failure Mechanism
When ingest(entries) calls process_batch(entries), process_batch stages merged entries into st['pending'] and st['view'] but does not call commit(st) or freeze_view(st). Because commit was removed, st['stable'] remains empty and st['meta']['frozen'] remains False. get_committed_total(st) (called by ingest) checks st['meta']['frozen'] and returns None. ingest_and_verify then computes view_digest from st['view'] (the staged order) and committed_digest via get_committed_digest(st), which returns None because st['meta']['frozen'] is False; the comparison view_digest == committed_digest therefore fails or yields inconsistent results. Tests expecting a frozen committed total and matching view vs committed digests fail because process_batch never performed the commit() and freeze_view() steps.

## Broken Invariant
After process_batch(entries) completes, st['meta']['frozen'] must be True and st['view'] must be exactly equal to st['stable'] (i.e., the materialized view reflects the canonical committed ordering).

## Fix Strategy
Reintroduce the commit(st) and freeze_view(st) calls into process_batch immediately after stage(st, merged). commit promotes pending to stable and sets meta['frozen']=True; freeze_view rebuilds view from stable. This ensures materialize(st) returns the committed, ordered view and selectors that require a frozen state (get_committed_total, get_committed_digest) behave correctly. The change is implemented by calling commit(st) and freeze_view(st) before returning.
