## Root Cause

        raise  # BUG: re-raises without rolling back reservation or reasoning_evaluator_audit entry`). Because place_order calls inventory.reserve(product_id, qty) and payment.add_audit_entry(...) before calling process(...), the exception handler never calls release(product_id, qty) or remove_audit_entry(order_id), so reserved state and the payment audit log are left unchanged on payment failure.

## Failure Mechanism
Concrete scenario: set payment._gateway_fail = True (via payment.set_gateway_fail(True)), then call place_order('P1', 2, 10). place_order calls reserve('P1', 2) which increments inventory._reserved['P1'], then calls add_audit_entry(...) which appends an entry to payment._audit_log, then calls process(...) which raises ValueError because _gateway_fail is True. The except clause re-raises the ValueError without calling release('P1', 2) or remove_audit_entry(order_id). As a result, inventory._reserved['P1'] remains incremented (reducing available stock) and payment._audit_log contains an orphan entry for the failed order. The code path that should undo those two side effects is never executed.

## Broken Invariant
If process(...) raises ValueError during place_order(product_id, qty, price), then after the call completes (with the exception propagated) the invariant must hold: inventory.get_reserved(product_id) equals its value before place_order was called, and payment.get_audit_log() must not contain any entry with order_id == f"ORD-{product_id}-{qty}". The current implementation violates this: on failure inventory.get_reserved(product_id) is increased by qty and payment.get_audit_log() contains an entry for the failed order.

## Fix Strategy
Wrap the call to process(...) in a try/except that, on ValueError, performs compensating actions in the same function before re-raising: call release(product_id, qty) to undo the earlier reservation and call remove_audit_entry(order_id) to remove the audit entry that was appended.
