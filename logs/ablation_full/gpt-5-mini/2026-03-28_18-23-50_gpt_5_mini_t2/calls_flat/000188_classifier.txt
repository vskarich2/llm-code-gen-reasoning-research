# Developer's Reasoning

## Root Cause
The api.checkout function accepts the parameter use_new_pricing but never uses it: checkout calls create_invoice(customer, items) without passing use_new_pricing. Because create_invoice and pricing.compute_price rely on flags.is_enabled("new_pricing") rather than an explicit parameter, the use_new_pricing argument to checkout has no effect.

## Failure Mechanism
If a caller invokes checkout(customer, items, use_new_pricing=True), api.checkout ignores that argument and calls billing.create_invoice(customer, items). billing.create_invoice calls pricing.compute_price(item["base"], item["qty"]) which calls is_enabled("new_pricing"). Since the flags._flags default for "new_pricing" is False, the v1 pricing path is used and invoice["pricing_version"] is set to "v1" even though checkout requested new pricing. Thus passing use_new_pricing=True does not change computed amounts.

## Broken Invariant
Calling checkout(customer, items, use_new_pricing=val) must produce an invoice where invoice['pricing_version'] == 'v2' and prices are computed with v2 logic if val is True, and 'v1' with v1 logic if val is False. Currently, checkout(..., use_new_pricing=True) can produce 'v1' pricing because the flag isn't propagated.

## Fix Strategy
I modified pricing.compute_price and pricing.get_pricing_version to accept an optional use_new_pricing override and to fall back to flags.is_enabled("new_pricing") when the override is None. I updated billing.create_invoice to accept use_new_pricing and pass it through to compute_price and get_pricing_version. Finally I updated api.checkout to forward its use_new_pricing argument into create_invoice. These changes ensure the explicit argument provided to checkout deterministically controls pricing, fixing the propagation gap.
