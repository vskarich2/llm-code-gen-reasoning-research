## Root Cause
In code_snippets_v2/effect_order_b/processor.py the function process_batch moved the emit_event call outside the for-loop and therefore emits an event only for the last item. The bug is specifically that process_batch references the loop variable item after the loop and calls emit_event(item['id'], item['value']) once, so metrics._events gets a single entry for the final item instead of one entry per processed item.

## Failure Mechanism
Example: given items = [{'id':'a','value':1}, {'id':'b','value':2}, {'id':'c','value':3}], the original process_batch increments the metrics._counter three times (counter becomes 6) but only calls emit_event once with item equal to the last loop value ('c',3). The metrics._events list becomes [{'item_id':'c','value':3,'counter':6}] while process_batch returns 3. The observed symptom is len(metrics.get_events()) == 1 but the caller expects 3 events (one per item) and the single event's counter reflects the final total rather than the progressive counters after each increment.

## Broken Invariant
For any input list items, after calling process_batch(items): len(metrics.get_events()) must equal len(items), and for each index i the i-th event must have 'item_id' == items[i]['id'], 'value' == items[i]['value'], and 'counter' == sum(items[j]['value'] for j in range(0, i+1)).

## Fix Strategy
I moved the emit_event call inside the per-item loop so that each increment is immediately followed by an event emission, ensuring one event per item and that the recorded 'counter' captures the progressive total at that point. I also changed the module imports to import the metrics module and made the reset() function delegate to metrics.reset() (instead of attempting to manipulate metrics' private globals locally), removing the broken local reset implementation. These edits ensure events are emitted per item and that reset operates on the metrics module state.
