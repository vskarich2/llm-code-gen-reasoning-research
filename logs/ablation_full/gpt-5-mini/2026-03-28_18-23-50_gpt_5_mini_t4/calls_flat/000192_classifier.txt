# Developer's Reasoning

## Root Cause
The function execute_transfer in code_snippets_v2/invariant_partial_fail/transfer_service.py mixes observability (ledger.audit) calls with the core balance-mutation logic: it mutates sender.balance and receiver.balance while also calling record_debit, record_credit, record_transfer_attempt, emit_failure_alert and emit_transfer_event. Because record_debit and record_credit are invoked inline with the balance changes, an exception raised after recording the debit (but before crediting) leads to a recorded debit without a corresponding credit while sender.balance has already been decreased.

## Failure Mechanism
Concrete scenario: sender.balance == 100, receiver.balance == 0, amount == 50. execute_transfer validates and records the transfer attempt, then subtracts 50 from sender.balance and calls record_debit(sender.account_id, 50). If random.random() < 0.3, the code emits a failure alert and raises RuntimeError before executing receiver.balance += amount and record_credit. The result is: sender.balance == 50, receiver.balance == 0, the ledger contains a debit entry for the sender but no credit entry for the receiver, and a failure alert was emitted. This produces an observable inconsistency between the in-memory balances and ledger entries and violates the intended atomicity of a transfer.

## Broken Invariant
Invariant: For any transfer attempt, if a debit record for amount A is present in the ledger (record_debit called) then either (a) a corresponding credit record for amount A must also be present and receiver.balance must have increased by A, or (b) the debit must not have been applied to sender.balance (i.e., the system must roll back the debit). Currently this invariant is violated when execute_transfer records the debit, mutates sender.balance, and then fails before applying/recording the credit.

## Fix Strategy
I separated pure business logic (balance mutations and validation) into small helpers that do not touch ledger or audit, and centralized all observability and alerting calls in the execute_transfer wrapper. Specifically I added _debit_account and _credit_account which perform only validation and balance updates, and left execute_transfer as the wrapper that calls record_transfer_attempt, record_debit, possibly emits failure alerts on simulated error, record_credit, and emit_transfer_event. By isolating side-effect-free balance operations from logging/alerting, the codebase now makes it straightforward to reason about and later enforce atomicity or introduce compensations; observability is no longer interleaved with core balance changes, reducing accidental coupling between logging and business invariants.

from audit import emit_transfer_event, emit_failure_alert


def validate_transfer(sender, amount):

        raise ValueError("amount must be positive")
    if sender.balance < amount:
        raise ValueError("insufficient funds")


# Core business logic helpers: pure balance mutations, no observability here.
def _debit_account(sender, amount):
    if amount <= 0:
        raise ValueError("amount must be positive")
    if sender.balance < amount:
        raise ValueError("insufficient funds")
    sender.balance -= amount


def _credit_account(receiver, amount):
    receiver.balance += amount


def execute_transfer(sender, receiver, amount):
    # Wrapper: observability and orchestration live here.
    validate_transfer(sender, amount)

    record_transfer_attempt(sender.account_id, receiver.account_id, amount)

    # Apply debit (business logic separated in helper)

    _credit_account(receiver, amount)
    record_credit(receiver.account_id, amount)
