# Developer's Reasoning

## Root Cause
In processor.process_batch the call to emit_event was placed outside the for-loop and referenced the loop variable 'item' after the loop. This meant emit_event was invoked exactly once with the final 'item' instead of once per item. Additionally, processor.reset attempted to reset module-level variables (_counter, _events) that are defined in metrics.py, so reset did not actually clear metrics' state.

## Failure Mechanism
For example, given items = [{"id": 1, "value": 2}, {"id": 2, "value": 3}]: process_batch calls increment twice (counter becomes 5), but because emit_event was called only once after the loop it appended a single event for the last item (id 2, value 3) and _events length is 1. Thus metrics.get_counter() == 5 while len(metrics.get_events()) == 1 and the recorded events don't correspond to each processed item.

## Broken Invariant
After processing a batch, the metrics module must satisfy: len(metrics.get_events()) == number_of_items_processed and sum(e['value'] for e in metrics.get_events()) == metrics.get_counter(). The code violated the first equality (events count != items processed).

## Fix Strategy
Call metrics.emit_event inside the per-item loop so an event is emitted for every item immediately after that item's increment. Replace the faulty local reset implementation in processor.reset with a call to metrics.reset so the metrics module's _counter and _events are actually cleared. These changes ensure one event per item and that reset clears the shared metrics state.
