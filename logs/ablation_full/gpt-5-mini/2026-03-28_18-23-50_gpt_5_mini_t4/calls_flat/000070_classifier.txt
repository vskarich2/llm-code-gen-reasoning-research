# Developer's Reasoning

## Root Cause
In processor.process_batch the audit_log call is placed after the for-loop and uses the loop variable 'item' that remains bound to the last item. This causes only a single audit entry (for the final item) instead of one per processed item.

## Failure Mechanism
When process_batch is called with multiple items, the code iterates and calls increment(...) and emit_event(...) for each item but only executes audit_log(item['id'], ...) once after the loop. For example, with items = [{'id':'a','value':1},{'id':'b','value':2},{'id':'c','value':3}] the function will create three increments and three events but only one audit entry for id 'c' (the last item). The per-item audit side-effect is therefore missing for all but the final item.

## Broken Invariant
After process_batch(items) returns, the number of audit entries must equal len(items) and each item's id must have a corresponding audit entry: len(audit.get_audit_log()) == len(items) and set(e['item_id'] for e in audit.get_audit_log()) >= set(item['id'] for item in items). Currently this is violated because only one audit entry is produced.

## Fix Strategy
Call audit_log for each item inside the processing loop so that an audit entry is appended per-item. Additionally, replace the broken reset implementation (which attempted to clear non-local globals) with delegating calls to the metrics and audit modules' reset functions to ensure proper state clearing. Moving audit_log into the loop fixes the missing-entry mechanism by executing the audit side-effect exactly once per item; delegating reset prevents NameError and ensures testable clean state.
