# Developer's Reasoning

## Root Cause
service.update_record wrote the new value only to the in-memory DB (db_write) and did not update the in-memory cache, while service.py also imported cache_invalidate even though update_record never calls it. Because update_record didn't write the new value into the cache, readers that hit the cache could still see a stale value.

## Failure Mechanism
A client calling put(key, value) runs update_record(key, value) which executes db_write("records", key, value). Immediately afterwards the API calls read_record(key). read_record first calls cache_get(key); if a stale value for key is present in _data from prior operations, cache_get returns that old value and read_record returns it without reading the DB. Thus the client receives the previous value despite the DB having been updated. Concretely: put -> update_record (db_write only) -> read_record -> cache_get returns stale value -> stale value returned to caller.

## Broken Invariant
After update_record(key, value) returns, a subsequent call to read_record(key) must return value (the value just written). This is testable: call update_record(k,v) then read_record(k) and assert the returned value == v.

## Fix Strategy
Ensure update_record updates the cache to reflect the DB write instead of relying on an invalidate step. I modified service.update_record to call cache_set(key, value) immediately after db_write so the cache and DB are consistent. I also removed the unused cache_invalidate import from service.py to eliminate the redundant invalidation reference. With cache_set performed after db_write, read_record will observe the fresh value via cache_get and the broken invariant is restored.
