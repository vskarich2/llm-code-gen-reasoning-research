# Developer's Reasoning

## Root Cause
make_transfer_b_to_a_steps acquires locks in the opposite order from make_transfer_a_to_b_steps: make_transfer_a_to_b_steps first calls acquire('A') then acquire('B'), while make_transfer_b_to_a_steps first calls acquire('B') then acquire('A'). This inconsistent ordering on the shared _locks dictionary (accessed via acquire/release) creates a circular lock dependency between transfers.

## Failure Mechanism
In interleaved_transfers the sequence (lock_ab, lock_ba, do_ab, do_ba) exercises the two-step locking. lock_ab executes step_lock_a() and calls acquire('A') so _locks['A'] becomes True. lock_ba then executes the step_lock_b() from make_transfer_b_to_a_steps and calls acquire('B') so _locks['B'] becomes True. When do_ab runs it calls acquire('B') (the second step of the A→B transfer) while _locks['B'] is already True, so acquire('B') raises RuntimeError("deadlock: B already locked"). The opposite ordering in make_transfer_b_to_a_steps is the direct cause of this circular wait: each transfer holds the other's desired lock and then tries to acquire the lock the other holds.

## Broken Invariant
All transfer operations must acquire the two account locks in a single, global, consistent order so that no circular wait is possible. Concretely, for these functions the invariant is: every transfer step sequence must call acquire('A') before acquire('B'). This is testable: running any interleaving of step functions produced by make_transfer_a_to_b_steps(...) and make_transfer_b_to_a_steps(...) must never result in a RuntimeError from acquire indicating "deadlock: <resource> already locked" due to circular lock ordering.

## Fix Strategy
I fixed make_transfer_b_to_a_steps so it acquires 'A' first and then 'B', matching make_transfer_a_to_b_steps. By enforcing the same global lock acquisition order (A then B) for both transfer directions, circular wait is eliminated: no interleaving can produce the situation where one transfer holds A and the other holds B while each waits for the other's lock. The change is implemented by swapping the order of acquire calls inside make_transfer_b_to_a_steps so its first step acquires 'A' and its second step acquires 'B' and performs the transfer.
