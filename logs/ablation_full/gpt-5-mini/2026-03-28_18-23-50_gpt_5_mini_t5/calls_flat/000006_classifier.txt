# Developer's Reasoning

## Root Cause
In config.create_config the line `config = DEFAULTS` returns a reference to the module-level DEFAULTS dict instead of a new dict. app._cached_settings stores that same dict reference, so any in-place updates (e.g. settings.update(...) in apply_overrides) mutate DEFAULTS and the cached object.

## Failure Mechanism
Sequence example: 1) First call get_settings() populates app._cached_settings with the dict returned by create_config(), but because create_config returned DEFAULTS by reference, _cached_settings is DEFAULTS. 2) Calling apply_overrides({'debug': True}) calls settings.update(overrides), which mutates the same DEFAULTS dict. 3) Subsequent calls to get_settings() return the cached dict (still referencing DEFAULTS) and now erroneously show 'debug': True even if the runtime overrides were intended to be ephemeral or defaults were later reset. Thus a caller sees stale/tainted default values because of shared references and in-place mutation.

## Broken Invariant
create_config(overrides=None) must return an independent dict so that mutating the returned dict does not change the module-level DEFAULTS. Concretely: after cfg = create_config(); cfg is not DEFAULTS (cfg is a separate object) and doing cfg.update({'debug': True}) does not change DEFAULTS['debug'].

## Fix Strategy
Make create_config return a shallow copy of DEFAULTS (config = dict(DEFAULTS)) so callers get an independent dict. Also simplify app loading by removing the cached reference: get_settings() now returns create_config() each call and apply_overrides() returns create_config(overrides) without mutating any shared object. This eliminates the shared-reference mutation path that caused stale/tainted cached settings.
