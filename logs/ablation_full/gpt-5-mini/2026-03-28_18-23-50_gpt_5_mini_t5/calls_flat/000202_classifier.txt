# Developer's Reasoning

## Root Cause
In cache_writer.py there were two separate functions—refresh_user_snapshot (which calls cache_put_if_absent) and sync_user_to_cache (which calls cache_put). They both manipulate the same underlying _store but with different semantics. user_service.py used refresh_user_snapshot after renaming a user, but refresh_user_snapshot's put-if-absent behavior meant it would not overwrite an existing cached name. The causal relationship: refresh_user_snapshot's use of cache_put_if_absent prevented cache updates when a rename expected an overwrite.

## Failure Mechanism
Concrete scenario: A user with id '42' exists and _store contains 'user:42' -> 'Alice'. rename_user(42, 'Alicia') updates the DB (db.update_name sets the new name) and then calls refresh_user_snapshot(updated). refresh_user_snapshot calls cache_put_if_absent(f'user:42', 'Alicia'), which does nothing because 'user:42' is already a key. As a result, cache_reader.get_display_name(42) still returns 'Alice' while lookup_user(42)['name'] returns 'Alicia', producing a stale display name.

## Broken Invariant
After rename_user(user_id, new_name) completes, get_display_name(user_id) must equal lookup_user(user_id)['name']. This invariant can be tested and was violated because refresh_user_snapshot did not overwrite existing cache entries.

## Fix Strategy
I replaced the two small, overlapping helpers with a single consolidated function sync_user_cache(user, force=False) in cache_writer.py. The function performs cache_put_if_absent when force=False (preserving warm/cold-cache semantics) and performs cache_put when force=True (explicit overwrite). I then updated all callers in user_service.py: save_user and bulk_warm_cache call sync_user_cache(user) (default put-if-absent) and rename_user calls sync_user_cache(updated, force=True) to ensure the cache is updated after a rename. This removes the ambiguity between the old helpers and ensures rename operations reliably update the cache when required.

    if force:
