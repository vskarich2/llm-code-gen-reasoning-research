## Root Cause
worker.process_item contains its own increment logic (it calls state.increment directly) while worker.quick_increment implements the same behavior; additionally state.py exposes a 'locked' flag and try_lock/unlock functions that add unused locking API surface. The duplication in worker (process_item vs quick_increment) is the direct cause of inconsistent/increased complexity.

## Failure Mechanism
Because process_item and quick_increment duplicate the increment behavior, a future change to quick_increment (for example adding validation, logging, or altering how the counter is updated) would only affect run_fast_pipeline (which calls quick_increment directly) and not run_pipeline (which calls process_batch_serial -> process_item). This divergence can lead to different totals between run_pipeline(items)['total'] and run_fast_pipeline(items)['total'], and could make run_verified raise a RuntimeError unexpectedly if only one path was updated. The presence of try_lock/unlock and the 'locked' flag in state.py increases the likelihood of such mistakes by exposing unused locking functions.

## Broken Invariant
For any list of items, run_pipeline(items)['total'] must equal run_fast_pipeline(items)['total']. This invariant can be broken if quick_increment and process_item diverge because process_item does not delegate to quick_increment.

## Fix Strategy
Centralize the increment behavior by making process_item call quick_increment so both pipelines share the same implementation, and remove the unused locking overhead from state.py (the 'locked' flag, try_lock, and unlock). This ensures a single canonical increment path and prevents divergence between run_pipeline and run_fast_pipeline.
