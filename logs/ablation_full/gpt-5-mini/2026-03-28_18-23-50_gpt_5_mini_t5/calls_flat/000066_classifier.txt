## Root Cause
In code_snippets_v2/effect_order_b/processor.py the function process_batch calls emit_event outside the for loop. The variable item therefore refers to the last iterated element when emit_event is invoked, so emit_event is executed only once per batch instead of once per item. Additionally, processor.reset attempted to assign to _counter and _events that are module-level variables in metrics.py, not in processor.py, which would raise a NameError if reset() were called.

## Failure Mechanism
Given a batch of three items, process_batch executes increment(item["value"]) three times (so metrics._counter increases correctly), but then calls emit_event(item["id"], item["value"]) once after the loop. As a concrete example: items = [{"id":1,"value":2},{"id":2,"value":3},{"id":3,"value":4}] results in _counter == 9 but _events contains only one event for item id 3 (with counter 9). This makes the number of emitted events not match the number of items processed. If processor.reset() were called, it would try to set _counter and _events in processor.py (which do not exist), producing a NameError and leaving metrics state uncleared.

## Broken Invariant

## Fix Strategy

Also make reset delegate to metrics.reset() to correctly clear the shared metrics state instead of touching undefined names. These changes ensure one event is emitted per processed item and that reset clears the actual metrics module state.
