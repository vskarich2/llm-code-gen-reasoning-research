# Developer's Reasoning

## Root Cause
cache_writer.refresh_user_snapshot uses cache_put_if_absent to write _store[f"user:{user['id']}"] = user['name'], causing updates to be ignored when a key already exists

## Failure Mechanism
When a user is created or renamed the code calls refresh_user_snapshot (cause) → refresh_user_snapshot calls cache_put_if_absent which does not overwrite an existing _store['user:{id}'] entry (mutation suppressed) → the cache remains at an older name while the DB row was updated (propagation) → cache_reader.get_display_name / format_user_label return stale names leading to visible stale user labels (observable failure). Example: rename_user updates the DB but because refresh_user_snapshot uses put_if_absent, the cache keeps the old name.

## Broken Invariant
After any operation that persists or updates a user (persist_user, sync_user_to_db, or db.update_name), the cache key 'user:{id}' must equal the latest user['name']; currently this invariant can be violated when refresh_user_snapshot uses cache_put_if_absent and thus does not update an existing entry.

## Fix Strategy
Consolidate the two helpers into a single canonical function sync_user_to_cache that always writes (uses cache_put) to ensure cache reflects the latest persisted user name. Update callers in user_service.py to call sync_user_to_cache. Provide a compatibility alias refresh_user_snapshot = sync_user_to_cache inside cache_writer.py to avoid breaking external code, but ensure internal callers use the canonical function. This breaks the causal chain because cache_put overwrites the stored name, so a rename or save will always update _store['user:{id}'] to the latest user['name'].
