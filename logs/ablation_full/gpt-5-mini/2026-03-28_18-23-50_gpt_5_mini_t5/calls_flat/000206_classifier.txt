# Developer's Reasoning

## Root Cause
In service.run_background_job the code calls get_defaults() which returns DEFAULTS with "timeout": 5. Because run_background_job reads get_defaults()["timeout"] it uses the hardcoded default timeout value 5 instead of the environment override defined in env_config._OVERRIDES ("timeout": 30).

## Failure Mechanism
When run_system_check() is called it composes the request and background results by calling handle_request() and run_background_job(). handle_request() calls get_config() (which calls defaults.get_defaults() and then updates with env_config._OVERRIDES), producing timeout 30. run_background_job() calls get_defaults() directly and therefore returns timeout 5. Concretely, run_system_check() returns {'request': {'timeout': 30, 'source': 'request'}, 'background': {'timeout': 5, 'source': 'background'}}, so the background job uses the wrong timeout.

## Broken Invariant
All consumers of configuration must observe env_config.get_config() semantics: the effective timeout must equal the value after applying env_config._OVERRIDES (i.e. get_config()["timeout"] == 30). Specifically, run_background_job() must return a timeout equal to get_config()["timeout"].

## Fix Strategy
Change run_background_job() to call get_config() instead of get_defaults(), so it receives the defaults merged with env_config._OVERRIDES. get_config() does: cfg = get_defaults(); cfg.update(_OVERRIDES); return cfg, which ensures the returned timeout is 30. This replaces the direct read of DEFAULTS (5) with the environment-overridden value (30).
