## Root Cause
In sender.py, the function send_with_retry calls send repeatedly in a for loop (for attempt in range(max_retries)) but does not stop (no return or break) when send succeeds. Because send performs append(msg) and notify(msg), a successful send in an early iteration is followed by additional send calls that append and notify the same message again. Additionally, sender.reset attempted to reset store state by assigning to _messages and _notifications local names (global _messages/_notifications were not defined in this module) instead of calling the store's reset, so reset() did not actually clear the store.

## Failure Mechanism
Concrete scenario: call send_with_retry('hello') with default max_retries=2 and fail_first=False. On attempt 0 send('hello') succeeds and calls append('hello') and notify('hello'). Because send_with_retry does not return/break after success, the loop continues to attempt 1 and calls send('hello') a second time, producing a second append and notification. The store ends up with two identical messages and two notifications even though the caller expected exactly one successful send. Separately, calling sender.reset() attempted to create local lists named _messages/_notifications instead of invoking the store.reset() function, so the store's _messages remained unchanged and the attempt counter could be reset while stored messages persisted.

## Broken Invariant
After a successful call to send_with_retry(msg, ...), the store must contain exactly one appended message for that msg; equivalently, when send does not raise any ConnectionError the number of stored messages must increase by exactly one. Also, calling sender.reset() must clear the store's messages and notifications (i.e., store.message_count() == 0 after reset).

## Fix Strategy
Stop retrying once send succeeds by returning immediately from send_with_retry inside the try block; this prevents duplicate append/notify calls. Also fix reset() to call the store's reset() function so that the store's _messages and _notifications are actually cleared. The change ensures a single successful send produces only one append/notify and that reset clears the shared store state.
