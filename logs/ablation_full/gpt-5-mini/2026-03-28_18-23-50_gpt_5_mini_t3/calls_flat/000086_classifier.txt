## Root Cause
In function retry_send the loop control is inverted: the code checks 'if not result: continue', so when send(msg) returns True on success the condition is False and the loop does not exit, causing subsequent iterations to call send again. The problematic variables/functions are retry_send, the local variable result, and the send function which appends to the global _sent list.

## Failure Mechanism
Concrete scenario: start with _sent == []. Call retry_send('hello', max_retries=2). Iteration attempt 0 calls send('hello'), which appends 'hello' to _sent and returns True. The code evaluates 'if not result' -> False, so it does not continue; execution proceeds to the end of the for-loop body and then to the next iteration (attempt 1). On attempt 1 it calls send('hello') again and appends a second 'hello' to _sent. The function then returns True, leaving _sent == ['hello', 'hello'] despite the first send succeeding.

## Broken Invariant
If send(msg) returns True on the first attempt, retry_send(msg, max_retries=N) must call send exactly once and therefore increase len(_sent) by 1. This is a testable invariant: after calling reset(); retry_send('m', max_retries=K) with send returning True immediately, get_sent() should return ['m'] (length 1).

## Fix Strategy
Change retry_send to stop retrying as soon as send returns truthy: return True immediately on success and only retry when send returns falsy; return False if all attempts fail. This prevents additional send calls after a successful send and preserves the semantic that a successful first attempt leads to a single send. Also implement clear_log to actually clear the _sent list by delegating to reset().
