# Developer's Reasoning

## Root Cause
In client.py the module-level variable _client_config is assigned once at import time via _client_config = get_config(). This captures the configuration dict returned by get_config() (and bound to the name _client_config) and prevents later calls from observing a newly loaded config after config.reset_config() is called.

## Failure Mechanism
Concrete scenario: on first import of client.py the call _client_config = get_config() loads the config with timeout 30. Later application code calls config.reset_config() and then causes the config to be reloaded (for example by calling config.get_config() or config.set_config()). However, client.get_timeout() returns _client_config['timeout'], which still refers to the original dict with value 30, so the client continues to return the old timeout despite the configuration having been reset and reloaded.

## Broken Invariant
The client API must reflect the current configuration: for any time t, client.get_timeout() must equal config.get_config()['timeout']. This invariant is violated because client.get_timeout() can return a stale value captured at import time instead of reading the current config.

## Fix Strategy
Remove the eager, import-time capture of the config (_client_config) and read the configuration on each access by calling get_config() inside get_db_url(), get_timeout(), and connect(). This ensures the client observes the latest dict returned by config.get_config() after reset_config() triggers a reload, eliminating the stale reference.
