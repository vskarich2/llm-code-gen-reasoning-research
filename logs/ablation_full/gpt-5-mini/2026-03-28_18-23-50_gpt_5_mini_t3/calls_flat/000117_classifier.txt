## Root Cause
In code_snippets_v2/temporal_drift_c/pipeline.py, the pipeline() function calls compute_raw_stats(normalized) (variable 'normalized' is the output of transforms.normalize). compute_raw_stats is documented to receive the original (untransformed) data (see metrics.compute_raw_stats docstring). By passing 'normalized' instead of the original 'data', compute_raw_stats receives transformed values instead of the raw inputs, causing the raw metrics to be computed from normalized values rather than the original values.

## Failure Mechanism
For example, given input data = [10, 20, 30], transforms.normalize(data) produces [0.0, 0.5, 1.0]. The pipeline currently does raw_stats = compute_raw_stats(normalized), so raw_max becomes 1.0, raw_min 0.0, raw_sum 1.5, raw_count 3 and derived raw_mean 0.5. The expected raw metrics are raw_max 30, raw_min 10, raw_sum 60, raw_count 3 and raw_mean 20.0. Thus downstream consumers that rely on raw_stats (or derived metrics) will receive incorrect numbers because compute_raw_stats was given 'normalized' instead of the original 'data'.

## Broken Invariant
The pipeline must satisfy: pipeline(data)['raw_stats'] == compute_raw_stats(data) for any input data (i.e., raw_stats MUST reflect the original untransformed input). Currently this invariant is violated because pipeline computes raw_stats from normalized data rather than the original data.

## Fix Strategy
Change the argument passed to compute_raw_stats from the normalized data to the original input 'data'. This directly restores the contract in metrics.py that compute_raw_stats receives the raw untransformed input, so raw_max/raw_min/raw_sum/raw_count and any derived metrics are computed from the original values. No other behavior is changed: normalization/clip/summarize_for_display continue to operate on transformed data, and derived metrics still come from the raw_stats computed from the original data.
