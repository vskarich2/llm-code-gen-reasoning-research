## Root Cause
In code_snippets_v2/effect_order_b/processor.py the function process_batch calls emit_event outside the for-loop and thus uses the loop variable 'item' after the loop has completed; as a result emit_event is invoked only once with the last item. Additionally, processor.reset attempts to reset globals _counter and _events in the processor module (setting local module globals) instead of delegating to the metrics module where those variables actually live.

## Failure Mechanism
When process_batch receives a list of items, the loop increments the shared counter for each item but does not emit an event for each item. For example, given items = [{'id': 'a', 'value': 1}, {'id': 'b', 'value': 2}], increment() is called twice so the metrics counter becomes 3, but emit_event is called only once (after the loop) with item == {'id': 'b', 'value': 2}. The metrics events list therefore contains a single event for 'b' while process_batch returns 2, causing len(get_events()) == 1 != 2 and missing the event for 'a'. The processor.reset function similarly fails to clear the metrics._counter and metrics._events because it manipulates names in the processor module instead of calling metrics.reset(), so tests expecting metrics.reset() behavior would also break.

## Broken Invariant
After calling process_batch(items), metrics.get_events() must contain exactly len(items) events in the same order as items (i.e., for all i, events[i]['item_id'] == items[i]['id']), and metrics.get_counter() must equal the sum(item['value'] for item in items). Currently the first part (one event per input item, in order) is violated.

## Fix Strategy
Call emit_event for each item inside the processing loop so an event is emitted per item immediately after the corresponding increment. Also make reset() delegate to the metrics.reset() function rather than trying to reinitialize names in the processor module. These changes ensure an event is recorded for every processed item and that reset clears the actual metrics state.
