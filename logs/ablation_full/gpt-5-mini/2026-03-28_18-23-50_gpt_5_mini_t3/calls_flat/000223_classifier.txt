# Developer's Reasoning

## Root Cause
The bug is in process(): it checks the global flag _initialized and, when False, appends an error to _log and returns False instead of preserving the item. Because process() never stores the item anywhere when called before init(), the item is lost. The causal variables are _initialized (the condition) and _log (where the code records the error instead of saving the item).

## Failure Mechanism
In broken_order() the first step calls process('a') while _initialized is False. process() executes the branch that does _log.append(f"error:not_init:{item}") and returns False; it does not save 'a'. Later init() sets _initialized = True and appends 'init' to _log, and process('b') appends 'processed:b'. Because 'a' was never buffered, the final log contains 'error:not_init:a' (an error entry) instead of 'processed:a', so the item is effectively lost from the successful processing flow.

## Broken Invariant
For any item X for which process(X) is called before shutdown(), the final log produced by shutdown() must contain the entry 'processed:X'. (This is testable by calling sequences of process/init/etc. and asserting that shutdown()'s returned log contains 'processed:<item>' for every process call.)

## Fix Strategy
Instead of logging an error when _initialized is False, buffer the incoming items in the global list _buffer. When init() runs it sets _initialized = True, appends 'init' to _log, then flushes _buffer in FIFO order by appending 'processed:<item>' entries to _log. reset() already clears _buffer, so initialization and tests behave deterministically. This ensures items submitted before init() are not lost but are processed once initialization happens.


# Task Description
process() runs before init() and items are lost. Fix so all items are processed regardless of arrival order.
