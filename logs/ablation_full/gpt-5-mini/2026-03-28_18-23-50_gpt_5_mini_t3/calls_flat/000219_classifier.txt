# Developer's Reasoning

## Root Cause
In make_withdraw_steps, the local mutable variable result['approved'] (set by step_check) is reused unchanged by step_act. step_act trusts this stale approval flag instead of verifying current state before calling do_withdraw, so the function pair implements a non-atomic check-then-act using result['approved'] that can become invalid after interleaving.

## Failure Mechanism
In interleaved_withdrawals(), two withdrawal step pairs are created for alice with balance 100 and amount 80. run_steps is called in the order (check_a, check_b, act_a, act_b). check_a sets its own result['approved']=True because check_balance('alice', 80) sees 100 >= 80. check_b also sets its own result['approved']=True for the same reason. Later act_a sees its stored result['approved']==True and calls do_withdraw('alice', 80), reducing the balance to 20. act_b then also sees its stored result['approved']==True and calls do_withdraw('alice', 80) again, reducing the balance to -60. Because step_act relied on the earlier check result rather than re-checking balance, two interleaved approvals lead to an overdraft.

## Broken Invariant
After any sequence of steps, get_balance(name) must never be negative. Concretely, for the scenario in this file: after two withdrawals of 80 from an initial balance of 100, get_balance('alice') >= 0 must hold. The current implementation can produce get_balance('alice') == -60, violating the invariant get_balance(name) >= 0.

## Fix Strategy
Make the act step verify the account balance at act-time instead of trusting the earlier stored result. I changed step_act in make_withdraw_steps to call check_balance(name, amount) at the time of withdrawal and only call do_withdraw when that check succeeds. This prevents a stale approval (result['approved']) from causing an overdraft under interleaving, because the second actor will see the reduced balance and decline to withdraw. The change preserves sequential behavior (a check immediately followed by its act still succeeds) while eliminating the TOCTOU race between separate check and act steps.

def check_balance(name, amount):

    return _accounts.get(name, 0) >= amount


def do_withdraw(name, amount):

    _accounts[name] = _accounts.get(name, 0) - amount


def run_steps(steps):
    results = []
    for fn, args in steps:
        results.append(fn(*args))
    return results

    """Split withdrawal into separate check and act steps.

    BUG FIX: avoid relying on a stale approval flag in the act step by
    re-checking the balance at act time. This prevents the TOCTOU race
    where two interleaved checks both pass and both acts withdraw.
    """
    result = {"approved": False}

    def step_check():
        result["approved"] = check_balance(name, amount)
        return ("check", result["approved"])

    def step_act():
        # Re-check at act time to avoid acting on a stale approval.
        approved_now = check_balance(name, amount)
        if approved_now:
            do_withdraw(name, amount)
            result["approved"] = True
        else:
            result["approved"] = False
        return ("act", result["approved"])

    return step_check, step_act
