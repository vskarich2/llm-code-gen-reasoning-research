In pipeline.find_best the function falls back to the module-level variable _last_best when no current record exceeds the threshold. Concretely, the for/else used 'else: best = _last_best', so find_best uses the previous call's value stored in _last_best instead of returning None. The causal relationship: _last_best is assigned only when a candidate is found (inside the loop), and the else clause reuses that stale value when the current input has no qualifying record.

## Failure Mechanism

A subsequent call with records whose values are all <= 50 should return None, but because the old code did 'else: best = _last_best' it returns the previous {"id":1, "value":60} instead. This manifests as silently returning stale data (incorrectly marking _pipeline_result = 'found'), which can cause downstream processing to operate on a record that does not actually meet the current input's filter criteria and may lead to incorrect computations or crashes elsewhere that expect None when nothing matches.

## Broken Invariant
The find_best function violates its documented contract: it must return the matching record or None if none qualifies. Specifically, for inputs where no valid record has value > threshold, find_best can return a previously stored record (the module-level _last_best) instead of returning None.

I also fixed reset() to only reset globals that exist in this module.
