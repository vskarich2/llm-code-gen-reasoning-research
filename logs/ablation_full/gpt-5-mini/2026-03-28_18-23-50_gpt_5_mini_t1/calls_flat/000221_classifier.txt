# Developer's Reasoning

## Root Cause
The bug is in process() using the module-level boolean _initialized to decide whether to handle an incoming item. When process() is called while _initialized is False it appends an error entry to _log and returns False, causing items submitted before init() to be dropped (see process(): if not _initialized: _log.append(f"error:not_init:{item}"); return False).

## Failure Mechanism
In broken_order(), run_steps calls process("a") before init(). Because _initialized is False, process() records an error (error:not_init:a) and returns False, and the item 'a' is never kept or later processed. Later init() sets _initialized True and process("b") is processed, so the final log lacks processed:a. Concretely: process()'s early return on !_initialized causes the function to neither buffer the item nor cause it to be processed after init(), so any pre-init inputs are lost.

## Broken Invariant
For any sequence of calls, every item passed to process(item) must eventually produce a 'processed:{item}' log entry after a subsequent init() call (i.e., items submitted before init() are not dropped). This file violates that: process('a') before init() produces 'error:not_init:a' instead of later producing 'processed:a'.

## Fix Strategy
Change process() to accept items even when _initialized is False by buffering them in the module-level _buffer instead of logging an error and returning. After init() sets _initialized True, flush the _buffer by emitting 'processed:{item}' entries for each buffered item. This preserves the original behavior for items arriving after init() while guaranteeing items submitted before init() are not lost.
