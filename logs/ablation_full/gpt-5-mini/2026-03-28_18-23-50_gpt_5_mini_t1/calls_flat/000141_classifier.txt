# Developer's Reasoning

## Root Cause
In limiter.should_allow the boolean expression uses the variables expired, under_limit, and exempt in the single return statement: `return not expired and under_limit or exempt`. Because of Python operator precedence this is evaluated as `((not expired) and under_limit) or exempt`, so the value of `exempt` can make the whole expression True even when `expired` is True. The bug is the incorrect grouping of `under_limit` and `exempt` in that return expression.

## Failure Mechanism
Concrete scenario: EXEMPT_CLIENTS contains 'internal-service' and a request from 'internal-service' has an expired token (is_expired(...) returns True). Suppose under_limit is False. Current code computes:
  expired = True
  not expired => False
  (not expired and under_limit) => False
  False or exempt => True
Thus should_allow returns True and the expired token is allowed through. This is caused directly by the return expression on the last line of limiter.py allowing `exempt` to override `expired` due to missing parentheses.

## Broken Invariant
The function should_allow must never allow a request when is_expired(timestamp, now, window_seconds) is True. Formally: for any inputs where is_expired(timestamp, now, window_seconds) == True, should_allow(...) must return False. The current implementation violates this invariant for exempt clients.

## Fix Strategy
Replace the ambiguous boolean expression with explicit grouping so that expiration is checked first and always blocks: return (not expired) and (under_limit or exempt). This enforces that if expired is True the whole result is False, while preserving the intent that exempt bypasses the limit only for non-expired tokens. No other logic or functions are changed.
