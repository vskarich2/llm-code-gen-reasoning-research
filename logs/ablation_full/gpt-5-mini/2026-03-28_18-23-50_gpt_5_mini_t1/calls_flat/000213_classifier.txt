# Developer's Reasoning

## Root Cause
The bug is in make_increment_steps(): it uses a captured dict (captured['current']) to store the read value and then step_write() writes captured['current'] + 1. Because step_write() uses the stale captured['current'] instead of the live global _value, a later write can overwrite an intervening increment.

## Failure Mechanism
Concrete interleaving: reset() sets _value = 0. make_increment_steps() for A and B produce (read_a, write_a) and (read_b, write_b). The interleaving run_steps([(read_a,()), (read_b,()), (write_a,()), (write_b,())]) does: read_a stores captured['current']=0, read_b stores captured['current']=0 (in its own captured dict), write_a executes _set(captured['current']+1) => _set(1), then write_b executes _set(captured['current']+1) => _set(1) again. The second write overwrites the first increment, leaving _value == 1 instead of 2.

## Broken Invariant
After performing two increments (in any scheduling of read and write steps), the global counter must increase by 2. Concretely, sequential_double_increment() and interleaved_double_increment() must both return 2. Currently interleaved_double_increment() can return 1.

## Fix Strategy
Change the write step so it does not rely on a previously captured read value. The updated step_write() computes the new value from the live global state (new = get() + 1; _set(new)). This guarantees each write performs an increment of the current _value at write time, so any interleaving of reads and writes cannot cause a lost update. The captured dict is removed because the write is based on get() at write-time rather than a stale capture.
