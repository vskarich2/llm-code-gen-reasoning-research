# Developer's Reasoning

## Root Cause
The bug is in transfer_service.execute_transfer: it mixes observability (ledger.record_debit / record_credit / record_transfer_attempt and audit.emit_*) with the core balance mutations and a simulated transient failure (the random.random() < 0.3 check). Specifically, execute_transfer subtracts amount from sender.balance, immediately calls record_debit(sender.account_id, amount), and only afterwards may raise RuntimeError during the simulated credit phase. The causal relationship is that record_debit is recorded before the possibility of a failure during credit, so the ledger can show a debit without a matching credit while the in-memory balances reflect the partial application.

## Failure Mechanism
Concrete scenario: suppose sender.balance = 100 and receiver.balance = 0 and amount = 30. execute_transfer validates, calls record_transfer_attempt(...), then does sender.balance -= 30 and immediately calls record_debit(sender.account_id, 30). If random.random() < 0.3 the code executes emit_failure_alert(...) and raises RuntimeError before increasing receiver.balance. Result: sender.balance is 70, ledger contains a debit entry for the sender (because record_debit was already called), but there is no corresponding credit entry for the receiver and no final transfer_attempt with status='failed' (only the initial pending). This produces a visible inconsistency between account balances and ledger/audit records.

## Broken Invariant
After execute_transfer returns or raises for a transfer of amount X from A to B, the ledger must record a debit of X for A iff A.balance decreased by X, and must record a credit of X for B iff B.balance increased by X; additionally there must be a transfer_attempt entry whose status is 'success' for successful transfers or 'failed' for failures. The current execute_transfer violates this: it can record a debit for A while failing before recording a credit for B and before recording a terminal transfer_attempt status.

## Fix Strategy
I separated the pure business logic into a helper _do_transfer(sender, receiver, amount) which only validates and mutates balances (and still simulates the transient failure). All calls to ledger.record_* and audit.emit_* were moved into the execute_transfer wrapper. The wrapper records the initial 'pending' attempt, captures initial balances, calls the helper, and after the helper returns or raises it inspects the actual balance changes to decide which ledger entries to append and which audit events to emit. On success it records debit, credit and a success transfer_attempt and emits the transfer event; on exception it records only the entries that reflect actual balance changes (e.g., a debit if the sender was already debited) and records a failed transfer_attempt and emits a failure alert before re-raising. This ensures the ledger and audit records are consistent with the final balances and that the transfer_attempt gets a terminal status.

from models import Account
from ledger import record_debit, record_credit, record_transfer_attempt
from audit import emit_transfer_event, emit_failure_alert


def validate_transfer(sender, amount):
    if amount <= 0:
        raise ValueError("amount must be positive")
    if sender.balance < amount:
        raise ValueError("insufficient funds")


def _do_transfer(sender, receiver, amount):
    """
    Core transfer logic: validate and apply balance changes.
    This helper performs only business logic (no ledger/audit calls).
    It may raise during the credit phase to simulate a transient failure.
    """
    validate_transfer(sender, amount)

    # Debit sender first
    sender.balance -= amount

    # Simulate transient failure during credit phase
    if random.random() < 0.3:
        raise RuntimeError("transient failure during credit")

    # Credit receiver
    receiver.balance += amount


def execute_transfer(sender, receiver, amount):
    """
    Wrapper that handles observability (ledger + audit) around the core transfer.
    It records a pending attempt, calls the core transfer, and then records ledger
    entries and emits audit events consistent with the actual balance changes.
    """
    # Record that a transfer was attempted (pending initially)
    record_transfer_attempt(sender.account_id, receiver.account_id, amount, status="pending")

    # Snapshot balances so we can determine what actually happened if an error occurs
    initial_sender_balance = sender.balance
    initial_receiver_balance = receiver.balance

    try:
        _do_transfer(sender, receiver, amount)
    except Exception as exc:
        # Determine what side-effects actually occurred on balances
        sender_delta = initial_sender_balance - sender.balance
        receiver_delta = receiver.balance - initial_receiver_balance

        # If the sender was debited in-memory, reflect that in the ledger
        if sender_delta == amount:
            record_debit(sender.account_id, amount)

        # If the receiver was credited in-memory (unlikely if credit fails), reflect that
        if receiver_delta == amount:
            record_credit(receiver.account_id, amount)

        # Mark the transfer attempt as failed and emit failure alert
        record_transfer_attempt(sender.account_id, receiver.account_id, amount, status="failed")
        emit_failure_alert(sender.account_id, receiver.account_id, amount, str(exc))

        # Re-raise so callers see the original failure
        raise
    else:
        # On success, both sides were updated: record both ledger entries and success
        record_debit(sender.account_id, amount)
        record_credit(receiver.account_id, amount)
        record_transfer_attempt(sender.account_id, receiver.account_id, amount, status="success")
        emit_transfer_event(sender.account_id, receiver.account_id, amount)
