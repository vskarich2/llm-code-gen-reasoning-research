## Root Cause
make_increment_steps -> step_read captures current value via get() into captured['current'] without performing the write; step_write later calls _set(captured['current'] + 1). The separated read (captured['current'] = get()) and later write (_set(...)) of the same captured value allows another increment to observe the same original _value before either write, causing a lost update.

## Failure Mechanism
Two increments A and B created by make_increment_steps each create their own step_read and step_write. If scheduling interleaves as: A.step_read (captured['current']=0) → B.step_read (captured['current']=0) → A.step_write (_set(0+1) sets _value=1) → B.step_write (_set(0+1) sets _value=1). Cause: non-atomic read-modify-write split across functions. Mutation: both closures read the same pre-update value and compute identical new value. Propagation: the second write overwrites the first's increment. Observable failure: get() returns 1 instead of the expected 2 after two increments.

## Broken Invariant
After performing two logical increments (two pairs of steps returned by two make_increment_steps calls, with any ordering of the four steps), get() should equal original_value + 2. The code violates this invariant under interleaving (observed get() == original_value + 1).

## Fix Strategy
Make the read+write happen atomically the first time either step_read or step_write is invoked for that increment pair, and make the second step a no-op that only reports the already-applied increment. Concretely, change make_increment_steps so that the first invoked step performs get(), computes new = current + 1, and calls _set(new), storing both 'before' and 'after' in the closure. Both step_read and step_write consult that closure: if the increment was already applied, they don't apply it again. This breaks the causal chain by removing the window between read and write where another increment can observe the same base value.

"""Counter with non-atomic read-modify-write, simulated via step functions."""

_value = 0


def reset():
    global _value
    _value = 0


def get():
    return _value


def _set(v):
    global _value
    _value = v


def run_steps(steps):
    results = []
    for fn, args in steps:
        results.append(fn(*args))
    return results


def make_increment_steps():
    """Split a read-then-increment into separate read and write steps.

    FIX: perform the read+write atomically on the first invoked step for this
    increment pair; make the second step a no-op that reports the already-
    applied increment. This prevents the lost-update where two increments
    both read the same value and both write value+1.
    """
    captured = {"done": False, "before": None, "after": None}

    def _perform_once():
        # Apply the increment exactly once for this increment-pair.
        if not captured["done"]:
            before = get()
            after = before + 1
            _set(after)
            captured["before"] = before
            captured["after"] = after
            captured["done"] = True
        # else: already applied

    def step_read():
        # On first call (either read or write), perform the increment.
        _perform_once()
        return ("read", captured["before"])  # return the observed-before value

    def step_write():
        # If increment hasn't been applied yet, apply it now. Otherwise noop.
        _perform_once()
        return ("write", captured["after"])  # return the value after increment

    return step_read, step_write


def sequential_double_increment():
    """Two increments, sequential: expect value=2."""
    reset()
    read_a, write_a = make_increment_steps()
    read_b, write_b = make_increment_steps()
    run_steps([(read_a, ()), (write_a, ()), (read_b, ()), (write_b, ())])
    return get()


def interleaved_double_increment():
    """Two increments, interleaved: fixed — both increments applied exactly once."""
    reset()

    read_b, write_b = make_increment_steps()
    run_steps([(read_a, ()), (read_b, ()), (write_a, ()), (write_b, ())])
