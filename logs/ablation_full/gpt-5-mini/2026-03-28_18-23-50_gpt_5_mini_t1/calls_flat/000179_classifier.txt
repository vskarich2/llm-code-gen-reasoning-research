# Developer's Reasoning

## Root Cause
reducers.stage only wrote the processed entries into 'pending' (st['pending'] = list(processed')) while reducers.commit was responsible for copying pending into 'stable' (st['stable'] = list(st['pending'])). In pipeline.process_batch and process_incremental the explicit calls to commit() and freeze_view() were removed, so 'stable' remained empty even after staging. At the same time, reducers.freeze_view rebuilt the view from 'stable' even though stage had already built the view from the processed entries (st['view'] = project(processed)). The concrete causal relationship: stage populated pending and view, but because pipeline no longer calls commit(), stable stays empty and materialize() (which returns items from st['stable']) reports an empty items list.

## Failure Mechanism
Given non-empty input entries, process_batch does: make_state -> normalize -> collapse -> stage(st, merged) -> materialize(st). Because stage only set st['pending'] and pipeline does not call commit(), st['stable'] remains []. materialize() returns {'items': list(st['stable']), ...} so the materialized output contains an empty items list. For example, calling process_batch([{'id':'a','val':1}]) results in st['stable'] == [] and materialized['items'] == [], even though merged contained the entry — the view was set but the canonical 'stable' items that materialize reports stayed empty.

## Broken Invariant
After process_batch(entries) or process_incremental(prev_state, new_entries) completes, materialize(st)['items'] must contain the merged/normalized items for the input (i.e., list(st['stable']) should equal the processed merged result). This invariant was violated because stage only populated pending and pipeline no longer called commit() to populate stable.

## Fix Strategy
Make stage the single operation that commits processed data: write the processed list directly into st['stable'], build st['view'] from that processed data, increment the version and mark the state frozen. Remove the separate commit() and freeze_view() responsibilities (they were redundant). Update state shape and related selectors/pipeline code so there is no reliance on a separate 'pending' field; recompute_view now projects from st['stable']. This ensures materialize() sees the same data that stage produced (st['stable'] is populated immediately), restoring the invariant that materialize() reports the processed items. Concretely, I updated make_state/copy_state to remove 'pending', changed reducers.stage to set 'stable' and 'view' and meta['frozen']=True, removed commit() and freeze_view(), adjusted selectors to no-op or reflect no pending state, and changed recompute_view to use st['stable'.
