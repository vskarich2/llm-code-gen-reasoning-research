# Developer's Reasoning

## Root Cause
In code_snippets_v2/partial_update_b/profile.py, the function update_profile updates user['first_name'] in the 'first_name' branch but does not recompute user['full_name']. The only place user['full_name'] is updated is inside the 'last_name' branch (user['full_name'] = user['first_name'] + ' ' + value), so changes to first_name (or certain ordering of simultaneous first/last changes) never produce a correct full_name.

## Failure Mechanism
If a user record starts as {'first_name': 'Alice', 'last_name': 'Smith', 'full_name': 'Alice Smith', ...} and update_profile(user, {'first_name': 'Alicia'}) is called, the function sanitizes and validates the new first name and sets user['first_name'] = 'Alicia' but does not update user['full_name']. As a result user becomes {'first_name': 'Alicia', 'last_name': 'Smith', 'full_name': 'Alice Smith', ...} — full_name is stale. Similarly, if changes contains both 'first_name' and 'last_name' and they are processed in an order where last_name is handled before first_name, the interim computation user['full_name'] = user['first_name'] + ' ' + value will use the old first_name, producing an incorrect full_name.

## Broken Invariant
After update_profile(user, changes) returns, it must hold that user['full_name'] == user['first_name'] + ' ' + user['last_name']. The current implementation can return a user where this equality is false (e.g., after a first_name update), violating this invariant.

## Fix Strategy
Recompute user['full_name'] from the stored user['first_name'] and user['last_name'] after applying all validated changes. This guarantees the invariant regardless of which name fields were updated or the iteration order. The change preserves existing validation (validate_name) and sanitization (sanitize_string) logic because the recomputation uses the already-updated user fields.
