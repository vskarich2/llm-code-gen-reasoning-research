# Developer's Reasoning

## Root Cause
pipeline.ingest is missing a break after a successful call to send_with_retry. In pipeline.py the for-loop 'for attempt in range(max_pipeline_retries):' always continues even when send_with_retry succeeds, so the pipeline calls send_with_retry again and causes additional successful sends. Additionally, pipeline.reset attempts to reset module-level variables _messages, _notifications and _attempt_count that are not defined in pipeline.py instead of calling the reset functions from the store and sender modules, so calling reset() does not reliably clear shared state.

## Failure Mechanism
Concrete scenario: ingest(msg, max_pipeline_retries=2, fail_first=True). On the first pipeline loop iteration send_with_retry(msg, max_retries=2, fail_first=True) will internally retry and eventually succeed, causing store.append(msg) to be called once. Because pipeline.ingest does not break after that success, the second pipeline iteration runs and calls send_with_retry again, which succeeds immediately and causes store.append(msg) to be called a second time. The result is two copies of the same message in the store. In other configurations (different max values) the combination of pipeline-level retries and sender-level retries can produce 3-4 total sends because each successful outer retry triggers one successful inner send that appends the message.

## Broken Invariant
Calling ingest(msg, ...) must cause the message to be appended to the store at most once. Formally: after a successful ingest(msg), store.get_messages().count(msg) == 1.

## Fix Strategy
Stop the pipeline-level retry loop once send_with_retry has succeeded by adding a break after the successful call. This prevents additional successful calls to send_with_retry that would append the same message again. Also replace the broken manual resets in pipeline.reset with calls to the store.reset() and sender.reset_sender() functions so shared module state is properly cleared instead of touching undefined names. These changes eliminate the extra appends while ensuring reset() behaves correctly.
