# Developer's Reasoning

## Root Cause
In pipeline.find_best the local variable 'best' is only created inside the for-loop when a record exceeds the threshold. If no record meets the threshold the code takes the else-path that assigns best = _last_best, so the function returns the module-level _last_best (from a previous successful call) instead of None. The causal relationship: find_best relies on _last_best as a fallback instead of returning None when no current record qualifies.

## Failure Mechanism
Concrete scenario: first call to find_best sees a record with value 75 and sets _last_best to that record. A later call with a new records list where no record has value > 50 will execute the for-loop without setting 'best'. The else branch currently assigns best = _last_best, so find_best returns the old record (stale data) and sets _pipeline_result to 'found', even though no record in the new input qualified. The stale return happens because the function falls back to _last_best rather than returning None when no candidate is found.

## Broken Invariant
The documented contract of find_best (in pipeline.find_best docstring) is: 'must return the matching record or None if none qualifies.' A failing test is: call find_best(records, rules) with records where no record has value > threshold; the function MUST return None. Currently it can return a non-None stale record (the previous _last_best), violating this invariant.

## Fix Strategy
Change find_best so that 'best' is initialized to None before the loop and only set when a current record exceeds the threshold. Update _last_best only when a new 'best' is found. Remove the fallback that assigns best = _last_best. This ensures find_best returns None when the current input has no qualifying record (satisfying the contract) and prevents accidental reuse of stale state. Concretely, I added best = None before the loop and removed the fallback assignment; _last_best is updated only on a successful match.
