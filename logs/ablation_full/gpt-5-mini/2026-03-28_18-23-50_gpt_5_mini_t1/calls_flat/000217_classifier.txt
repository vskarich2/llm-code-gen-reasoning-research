# Developer's Reasoning

## Root Cause
In make_withdraw_steps, the step_act closure relied on the cached result['approved'] value set earlier by step_check and unconditionally called do_withdraw when that cached flag was True. The causal relationship is: step_check sets result['approved'] based on a moment-in-time check_balance(name, amount); step_act then uses that stale result['approved'] instead of re-checking the account, so an interleaving of two step_check calls can set result['approved'] True for both withdrawals and both step_act calls will withdraw using the stale flag.

## Failure Mechanism
Concrete scenario using the code: sequentially run run_steps([(check_a, ()), (check_b, ()), (act_a, ()), (act_b, ())]) with alice starting at 100. check_a sets result['approved']=True (100 >= 80). check_b then sets its own result['approved']=True (still 100 >= 80). act_a reads its result['approved'] (True) and calls do_withdraw('alice', 80), leaving balance 20. act_b then reads its cached result['approved'] (also True) and calls do_withdraw('alice', 80) again, leaving balance -60. The bug manifests because step_act used the earlier cached approval rather than consulting the current _accounts state via check_balance before debiting.

## Broken Invariant
After any sequence of check/act steps produced by make_withdraw_steps for withdrawals, get_balance(name) must never be negative. Specifically: for any account name and non-negative amount, executing any interleaving of the check and act steps returned by make_withdraw_steps must preserve get_balance(name) >= 0.

## Fix Strategy
I changed the step_act closure so it does not act on the stale result['approved'] flag; instead it re-evaluates the current account state by calling check_balance(name, amount) immediately before calling do_withdraw. This ensures the ACT consults the current balance and only debits when there are sufficient funds. The modification prevents the interleaving scenario where two checks both see sufficient funds but only the first debit should succeed.

_accounts = {}


def reset():
    _accounts.clear()


def create_account(name, balance):
    _accounts[name] = balance


def get_balance(name):
    return _accounts.get(name, 0)


def check_balance(name, amount):
    """CHECK: is balance sufficient?"""
    return _accounts.get(name, 0) >= amount


def do_withdraw(name, amount):
    """ACT: decrement balance. Assumes caller verified."""
    _accounts[name] = _accounts.get(name, 0) - amount


def run_steps(steps):
    results = []
    for fn, args in steps:
        results.append(fn(*args))
    return results


def make_withdraw_steps(name, amount):
    """Split withdrawal into separate check and act steps.

    The ACT must consult current state before debiting to avoid acting on
    a stale approval from a prior CHECK.
    """
    # keep an approval flag for the CHECK step to report, but do not let
    # the ACT blindly trust that cached flag
    result = {"approved": False}

    def step_check():
        result["approved"] = check_balance(name, amount)
        return ("check", result["approved"])

    def step_act():
        # Re-check current balance immediately before withdrawing so
        # the ACT uses up-to-date state instead of any previously cached
        # approval that may be stale due to interleaving.
        allowed = check_balance(name, amount)
        if allowed:
            do_withdraw(name, amount)
            result["approved"] = True
        else:
            result["approved"] = False
        return ("act", result["approved"])

    return step_check, step_act


def sequential_withdrawals():
    """Two withdrawals of 80 from balance=100. Sequential: second denied."""
    reset()
    create_account("alice", 100)
    check_a, act_a = make_withdraw_steps("alice", 80)
    check_b, act_b = make_withdraw_steps("alice", 80)
    run_steps([(check_a, ()), (act_a, ()), (check_b, ()), (act_b, ())])
    return get_balance("alice")
