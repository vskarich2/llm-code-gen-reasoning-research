# 🎯 First: Clarify the goal (this matters)

> **induce predictable, reproducible mismatches between reasoning and execution**

# 🔥 The key insight (this is the core of everything)

There are **two directions of dissociation**:

## 1. LEG (Reasoning → correct, Execution → wrong)

This happens when:

> the *mapping from reasoning → code* is fragile

---

## 2. Lucky Fix (Reasoning → wrong, Execution → correct)

This happens when:

> the *mapping from code → correctness* bypasses reasoning

---

# 🧠 You should NOT design cases randomly

You should design them using **failure generators**

Think in terms of:

```text
mechanism → predictable dissociation
```

---

# 🧪 Part 1 — How to induce LEG reliably

You want:

> reasoning succeeds, but implementation fails

This means:

* the reasoning step is easy
* the execution step is fragile

---

## 🔧 LEG Generator Patterns

### 1. **Correct invariant, fragile implementation**

Example:

* “must update all dependent fields”
* model understands this
* but misses one field

👉 This gives:

* reasoning correct
* execution fails

---

### 2. **Alias / identity traps**

Model knows:

> “don’t mutate shared state”

But:

* forgets `.copy()`
* or mutates nested structure

👉 extremely reliable LEG

---

### 3. **Correct branch, wrong variable**

Model identifies:

> “this condition is wrong”

But:

* fixes condition
* uses wrong variable in assignment

---

### 4. **Multi-step transformation drift**

Model knows:

> “normalize → select → commit”

But:

* uses wrong representation at commit stage

This is your current strength—keep it.

---

### 5. **Spec → implementation gap**

Model correctly explains:

> “we need X behavior”

But:

* code doesn’t actually implement X fully

---

### 6. **Correct logic, wrong placement**

* fix exists
* but applied in wrong function / stage

---

### 7. **Off-by-one / boundary leakage**

Reasoning is trivial:

> “include all elements”

Execution fails:

* misses last element
* wrong index

👉 simple but powerful LEG isolator

---

## ⚠️ Key rule for LEG cases

You must ensure:

> reasoning correctness is **unambiguous**

If reasoning is even slightly ambiguous, reviewers will say:

> “maybe reasoning wasn’t actually correct”

---

# 🧪 Part 2 — How to induce Lucky Fix reliably

This is harder—but more valuable.

You want:

> reasoning wrong, execution correct

---

## 🔧 Lucky Fix Generator Patterns

### 1. **Overfit pattern recall**

Model applies:

* known fix pattern
* even if reasoning explanation is wrong

Example:

* “add .copy()”
* explanation is nonsense
* but code is correct

---

### 2. **Shallow heuristic success**

Model:

* misidentifies cause
* but applies a transformation that coincidentally fixes it

---

### 3. **Symmetric solution space**

Multiple valid fixes exist:

* model picks one
* reasoning describes a different one

---

### 4. **Redundant invariants**

System has:

* multiple ways to satisfy correctness

Model:

* misunderstands mechanism
* but enforces invariant another way

---

### 5. **Spec ambiguity exploitation**

Prompt is ambiguous:

Model:

* interprets incorrectly
* but tests still pass

---

### 6. **Dead reasoning path**

Model gives:

* completely wrong explanation

But:

* code patch is independent of explanation

👉 extremely powerful signal

---

## ⚠️ Key rule for Lucky Fix

You must ensure:

> reasoning is **clearly wrong**, not just incomplete

Otherwise:

> reviewers will say “partial correctness”

---

# 🧱 Part 3 — Designing a GOOD targeted case

Each targeted case should have:

## 1. A clean invariant

Example:

> “selected candidate must correspond to original selection”

---

## 2. Multiple plausible hypotheses

At least:

* 2–3 believable causes

---

## 3. A trap

A fix that:

* looks right
* fails

---

## 4. A correct fix that is:

* simple in reasoning
* fragile in implementation (for LEG)
  or
* simple in implementation
* misaligned with reasoning (for Lucky Fix)

* **3–5 mixed / ambiguous**

You are designing:
